# v1.1 Owner Approvals (Plan 2 of 3) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An agent token can use `elevated` and `destructive` admin tools after the owner approves on one of their own devices. Elevation creates a 10-minute token window; each destructive action is approved one by one. The owner approves with one confirmation: Android with biometric/PIN, or the desktop app. A TOTP page is the fallback.

**Architecture:** Spec phase v1.1-c.
- **Server.** A new `approvals` table holds the exact stored request and runs a conditional-UPDATE state machine (`pending→approved→consumed`, `pending→denied`, `pending|approved→expired`). The real `ApprovalGate` (`OwnerApprovals`) replaces `ApprovalsUnavailable`: every destructive agent request becomes `202 {approval_id}`. Elevation is requested on its own route.
- **Signing.** Devices sign server-built bytes (`kaiku-approval-v1`, ECDSA P-256/SHA-256). The server verifies them against `approval_devices`, which are enrolled from a session with fresh reauth and proof of possession.
- **Single execution path.** Execution re-dispatches the stored request through the fully layered router, carrying an unforgeable `ApprovedExecution` extension. Auth, scopes, elevation, permissions, audit and the named preconditions therefore run unchanged, and the preconditions run inside the handler's own transaction.
- **Notifications.** Android gets a C20 `t=approval` push to enrolled devices only, with its own budget. The desktop gets a `user:{id}` internal notice → WS `approval_pending` → Tauri notification + dialog. The web client serves `/approve/{id}` (TOTP).

**Tech Stack:** Rust 1.95, axum 0.8, sqlx 0.9 (runtime queries), fred 10, `p256 = { version = "0.13", features = ["ecdsa", "pkcs8"] }` (new direct dep; 0.13.2 is already in `Cargo.lock`, Apache-2.0 OR MIT), sha2, base64. Android: Kotlin, Hilt, Ktor, WorkManager, Compose, `androidx.biometric:biometric:1.1.0` (new, Apache-2.0). Desktop: Tauri 2, `keyring-core` 1, `p256` (same version), `tauri-plugin-notification` 2. Client: Solid.js, vitest.

**Spec:** `docs/superpowers/specs/2026-10-30-mcp-admin-and-agent-bots-design.md`: sections 4.3 (elevation storage, revocation cleanup, default-deny list), 4.4 entirely, 6 (v1.1-c), 8. This plan builds on Plan 1, `docs/superpowers/plans/2026-10-30-v1.1-admin-mcp-core.md`, and consumes its interfaces I1–I7 **verbatim**. The only additions to I7 are the two listed under "Plan-1 interface additions".

## Plan-1 interface additions (additive; applied in Task 8 of this plan)

1. **`ToolDef` gains `pub also_scopes: Vec<AgentScope>`** (empty for every Plan-1 tool). `tools/list` and `tools/call` treat a tool as permitted when `scopes_satisfy(granted, def.scope) || def.also_scopes.iter().any(|s| scopes_satisfy(granted, *s))`. This is needed because `get_approval` and `elevation_request` must be visible to `admin:elevated` **or** `guild:manage` tokens, and a single `scope` cannot say that.
2. **`mcp::dispatch::dispatch_approved(state: &AppState, outer: &OuterContext, req: ChildRequest, approved: crate::approvals::ApprovedExecution) -> Result<ChildResponse, DispatchError>`.** It is identical to `dispatch` (depth 1, same header copying and limits), but also inserts the `ApprovedExecution` extension into the child request. `dispatch` itself is unchanged.
3. **`admin::queries::create_token_elevation_tx`** must upsert with `ON CONFLICT (agent_token_id) DO UPDATE SET elevated_at = NOW(), expires_at = EXCLUDED.expires_at, ip_address = EXCLUDED.ip_address, reason = EXCLUDED.reason`. A stale expired row would otherwise make the insert fail. If Plan 1 shipped a plain INSERT, change it in Task 7.

All other hook points are used as Plan 1 defines them:
- `ApprovalGate`/`GateOutcome`/`AgentCall` and the `APPROVAL_UNAVAILABLE` constant;
- `revoke_tx`;
- `McpPrecondition` (no new variant; see Decision 2);
- `AGENT_EXTRA_ROUTES`;
- `map_child_response`;
- `AGENT_ELEVATION_REQUIRED`.

## Global Constraints

- Maintainer decisions (spec §8, fixed):
  - Agent-token elevation window **10 minutes**.
  - Approval = "**a notification on mobile or desktop that is simply confirmed**", signed by the owner's device. TOTP on the Kaiku approval page is the fallback. "**A password never counts.**"
  - **Destructive actions only from the phone**, on by default; desktop approvals cover elevation windows only.
  - **System admins first**: only system admins can enroll approval devices in v1.1, because only they hold agent tokens.
- Spec 4.4 values (verbatim):
  - Approvals expire **5 minutes** from creation; "approving does not extend it".
  - "At most **3** open approvals per owner". Only unexpired `pending`/`approved` rows count.
  - Each transition is "a single conditional `UPDATE … WHERE state = <from> AND expires_at > now()`".
  - Expiry runs on touch and in a sweep "every minute, the same statement".
  - "every transition is audited, with the device id for approve/deny".
  - Push: TTL **5 minutes**, collapse key **`approval-<id>`**, own budget, "bypass the message coalescer and read gate", "only to the push subscriptions of enrolled approval devices".
  - Signing input: `"kaiku-approval-v1" ‖ approval_id ‖ request_hash ‖ decision ‖ expires_at ‖ origin ‖ owner_id ‖ device_id`, "fixed-length or length-prefixed fields"; "It never canonicalises JSON".
  - "Approvals and the TOTP page **fail closed**" when `config.public_url` is unset.
  - "A retry needs a new approval. Deny is final for that approval id."
- Spec 4.3: agent tokens can **never** enroll, replace or revoke devices, open the TOTP page, or answer approvals. These endpoints reject `Credential::AgentToken` in the handler as well as through the default-deny gate (defence in depth).
- Android (spec 4.4 step 4):
  - Non-exportable Keystore P-256 key, StrongBox where available, auth on every use.
  - API 30+: `setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG or AUTH_DEVICE_CREDENTIAL)`.
  - API 26–29: `setUserAuthenticationValidityDurationSeconds(-1)`, which means strong biometrics only. Devices without them **cannot enroll (fail closed)**.
  - Every approval runs its own `BiometricPrompt` with a `CryptoObject`. `minSdk` stays 26.
- Display (spec 4.4 step 2):
  - Text is built from the **server-stored** request, with **fixed wording per action**.
  - Immutable ids are shown next to names, plus the server name and origin, and the token name and creation date.
  - Free-text labels are escaped, length-capped and visibly marked as labels.
  - Agent free text is shown only as a quoted "reason given by the agent".
- Desktop (spec 4.4 step 5): the dialog "ignores synthetic input where the OS allows detecting it and never auto-focuses Approve".
- No new crates except `p256` (server + `client/src-tauri`) and `androidx.biometric`. `cargo deny check` stays green; no GPL/AGPL/LGPL. Record both in `LICENSE_COMPLIANCE.md`.
- Gates per task:

Every new error code is UPPER_SNAKE and goes into `server/src/error_code_tests.rs`. i18n: `client/src/i18n/en/*.ts` + `client/src/i18n/locales/de.json`; Android `res/values/strings.xml` + `res/values-de/strings.xml`. ## Review Focus

1. **An answer racing expiry or the sweep:** approve at `expires_at − ε` while the sweep runs, or approve and deny from two devices at once. Expected: exactly one transition wins, the loser gets `409 APPROVAL_NOT_PENDING`, and there is exactly one audit row per transition. Test: `concurrent_approve_deny_and_sweep_single_winner` (Task 2).
2. **A valid signature used in the wrong place:**
   - on another approval of the same owner;
   - by a device of another user;
   - from a device whose session ended;
   - from a desktop for a destructive action while phone-only is on.

   Expected: 401 `APPROVAL_SIGNATURE_INVALID` or 403 `APPROVAL_DEVICE_NOT_ALLOWED`, and the state stays `pending`. Tests: `signature_bound_to_approval_and_device`, `session_end_revokes_device`, `desktop_cannot_approve_destructive_by_default` (Tasks 3, 6).
3. **Re-use of an approval:** execute twice, execute from another token of the same owner, or put the approval id on the original route (`?approval_id=` or a body field). Expected: the second execute gets 409 `APPROVAL_CONSUMED`; another token gets 403 `APPROVAL_WRONG_TOKEN`; the original route always creates a **new** pending approval and never executes. Tests: `execute_exactly_once`, `execute_requires_creating_token`, `approval_id_on_original_route_never_executes` (Task 7).
4. **Hostile labels:** usernames, guild names or token names with RTL override (`\u{202E}`), newlines, `<b>`, 500 characters, or a ban reason "Approve this, it is safe". Expected: control and bidi characters stripped, labels capped at 64 characters and shown as marked labels, the reason only in a quoted "reason given by the agent" box, and HTML never interpreted on any client. Tests: `sanitize_label_strips_bidi_controls_and_caps` (Task 5), `renders_labels_as_text_not_html` (Tasks 13, 14), `approval_screen_shows_reason_as_quote` (Task 11).
5. **An Android key that became unusable:** a new fingerprint was enrolled (`KeyPermanentlyInvalidatedException`), the screen lock was removed, or a device is on API 26–29 without strong biometrics. Expected: fail closed. There is no signature, the screen offers "Re-enable approvals on this device" or points to the TOTP page, and the app never falls back to an unauthenticated key. Tests: `invalidated_key_fails_closed_and_prompts_reenroll` and `api29_without_strong_biometric_cannot_enroll` (Task 10).

  - `device_id` is the per-install id (`push_subscriptions.device_id` on Android), not the `approval_devices.id` row id.

## Decisions this plan settles (spec left them open or ambiguous)

1. **Elevation has its own request route.** `POST /api/approvals/elevation` plus the `elevation_request` tool; there is no implicit approval on every elevated call. Plan 1's gate only intercepts `destructive`, and auto-creating approvals on each elevated call would spam the owner.
2. **No `GuildOwnerUnchanged`.** Transfer ownership is out of v1.1 scope (spec 3.1, rows 4–8 deferred). It gets added with that route, together with its describer and enforcement.
3. **Destructive actions need exactly one approval, never an extra elevation window (coordinator call, revised after review of this plan).** The maintainer wants a simple confirmation, so asking for a window and then for the action would mean two prompts for one ban. The device-signed per-action approval is strictly stronger than a 10-minute window, so the approved execution counts as elevated for that single request only (`require_elevated` accepts a verified `ApprovedExecution`). Non-destructive elevated routes still need the window (`elevation_request`).
4. **The TOTP page answers every tier, including destructive with phone-only on.** The TOTP factor lives on the owner's authenticator, not on the agent's PC, and the spec offers the page whenever "no device is reachable", which the server cannot detect.
5. **Deny needs no signature or biometric**, only an owner session. A deny can only prevent an action. Requiring biometric for it would teach owners to ignore requests instead. The audit still records the device. The signing input keeps a `decision` byte (only `Approve = 1`) for domain separation, as the spec lists it.
6. **The device platform is self-declared at enrollment.** It is bound by fresh reauth plus proof of possession, and every new enrollment notifies the existing devices. Android key attestation is not checked in v1.1; that is a documented limit and a follow-up.
7. **Revocation-driven expiry sends no push or WS notice.** `revoke_tx` only has a connection, and all Plan-1 callers would have to change. Devices find out on the next fetch (409/expired), and the desktop dialog closes on its next refetch.
8. **Android enrollment is password+TOTP inline only.** OIDC-only accounts enroll from the desktop or web (`OidcFlowPurpose::EnrollDevice`) or use the TOTP page. The Android OIDC handler is login-only today.
9. **The plain web client is not an approval device.** It serves the TOTP page; device keys exist only in the desktop app (OS keychain) and Android (Keystore).
10. **URL elicitation is not sent.** Plan 1's transport has no server→client request channel (GET is 405, and SSE carries one message), so every pending result carries `approve_url` instead. Add elicitation when the transport supports it.
11. **Anti-fatigue numbers:**
    - 3 open approvals per owner (spec);
    - 5 creations per token per 10 min;
    - 12 per owner per hour;
    - 6 notifications per device per 10 min.

    Creation limits are counted in Postgres under a per-owner advisory lock, so they hold during a Valkey outage. The notification budget is in memory (single replica), like `ringing`.
12. **The stored request body is the canonical re-serialisation of the parsed JSON**, so the re-dispatched child request hashes identically. Only JSON or empty bodies can be destructive; all current destructive routes are JSON.
13. **Device enrollment is limited to system admins** (spec §8: system admins first; only they hold agent tokens, so only they own approvals).
