# v1.0 L2: client login (desktop/web and Android) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship every client side of the v1.0 login: on desktop and web the phone-QR sign-in, password and SSO sign-ins confirmed by a scan, probation sessions with a passkey upgrade path, passkey step-up, security settings and log, the read-only Kaiku DM, recovery and "Secure my account", registration tickets and the admin views; on Android the phone as a user-verified key (Keystore P-256, UV on every signature), the scanner with origin pinning, the approval and setup screens, device-key sign-in, step-up, notices and the admin's "Set up a phone".

**Architecture:** Two disjoint sections for two parallel writers. **Section A** (desktop/web, `client/**`) adds a login-flow store that drives the C27 attempt machine by long-poll (cookies in the browser, the verifier kept in Rust on the desktop), a passkey-only step-up helper on top of LP's ceremonies, and new security, notice and request screens; pre-session secrets never reach the webview. **Section B** (Android, `mobile/android/**`) adds an `approval` package (C26 codec, challenge verifier, Keystore key, UV prompt, signer) under every device signature, a key-device repository that outlives sessions, and screens for scanning, approving, setting up, issuing setup codes and admin work. Both sections only consume server contracts; no server file is touched.

**Tech Stack:** Solid.js + TypeScript (vitest, `@solidjs/testing-library`, `qrcode`), Tauri 2 / Rust (`reqwest`, `keyring-core`, `zeroize`, `wiremock` in tests); Kotlin 2.1, Compose, Hilt, Ktor, ML Kit + CameraX (existing), `androidx.biometric` 1.1.0 and `com.google.zxing:core` 3.5.3 (new), JUnit/MockK/Turbine.

Package cut (coordinator notes, 2026-11-03): L2 in 2.2, hotspots in 2.4; where the cut predates the spec (approval push, number matching, possession-only keys, `t=approval`), the spec wins. ## Global Constraints

- **Wire (C26–C29 common rules):** JSON `snake_case`; ids lowercase hyphenated UUID strings; times RFC 3339 UTC except integer Unix seconds inside signed contexts; binary values base64url without padding (b64u); clients ignore unknown fields and map unknown enum values to an `unknown`/`UNKNOWN` member (C5).
- **Errors:** body `{"error": CODE, "message": string}` plus listed fields (`tries_left`, `recovery_codes_left`, `ready_at`, `state`, `reason`); user text only through `errorText(code)` (web) or string resources (Android), never the server `message` (C16). 429 `TOO_MANY_ATTEMPTS` carries `Retry-After`; 503 `SERVICE_UNAVAILABLE` on outage.
- **Client class:** the desktop sends `X-Kaiku-Client: desktop` on every session-creating call; Android sends `X-Kaiku-Client: android` on every request. Native clients get secrets in bodies and keep them in Rust / Keystore-wrapped storage; browsers get them only as `HttpOnly; Secure; SameSite=Strict` path-scoped cookies (`__Secure-kaiku_attempt`, `__Secure-kaiku_request`, `__Secure-kaiku_ticket`, `__Secure-kaiku_enroll`). The desktop webview never sees tokens, verifiers, collection secrets, request secrets or tickets (spec Constraints).
- **Fixed copy (spec wording, English; German stays fallback):**
  - F3 neutral answer: "Wrong username or password, or password sign-in is not available for this account. Use a passkey or 'Sign in with phone', or ask an admin."
  - F3 confirmation QR: "Open Kaiku on your phone and scan this code." and "Phone not at hand?"
  - F2 context question: "Are you signing in on a PC in front of you right now?" with "Yes, sign in", a prominent "No" and a smaller "I didn't start this".
  - Stale scan: "This code has just changed – scan the new one".
  - F5a typing screen: "A device calling itself '<label>' wants to become your key" and "Type the code from the device in your hand. Never type a code someone tells you."
  - F5c new phone: "Set up Kaiku for <name> on <server>?"
  - F6 entry: "I lost my phone / forgot my password" and "Phone stolen, and someone may know its screen lock? Ask an admin to remove it now."
  - SM3 refusal: "Name and confirm a recovery contact first, or use the host CLI".
  - Admin-setup prompt: "Set up by <admin>. If that is right, there is nothing to do."
  - B.6.6 warnings before a repudiation: `voids_own_request` → "This also stops your own request to secure your account"; `voids_own_bootstrap` adds "afterwards only an admin can help".
  - UV prompt title "Confirm it's you" (the phone's own screen lock; never a separate Kaiku PIN).
- **Timers and limits (C26/C27):** QR token 60 s; attempt ≤ 10 min; claim challenge 2 min; collect ≤ 60 s after `approved`; long-poll `wait` 0..25 s; setup token 10 min, single use; enrolment code 6 digits, 5 min from the claim, 3 tries; ≤ 5 open setup codes per issuer (409 `ENROLLMENT_LIMIT`); registration ticket 30 min; request delay `ACCOUNT_REQUEST_DELAY_HOURS` 24 (24–72), Finish within 24 h of `ready`; step-up grant ≤ 300 s, single use, bound to the `sid`; device clock skew for `expires_at` 60 s; at most 50 live sessions; refresh: browser 30 d / desktop and Android 90 d absolute cap, 7 d sliding.
- **Assurance (CC4, B.4):** a session is `full` only when a passkey or a device-key signature created it; everything else is `probation` for life. Probation may: chat, DMs, calls, profile name and photo, notification settings, read the security log, sign itself out, owner rule part 2. Nothing upgrades a session; "Sign in with a passkey" makes a new full one. A token without the `assurance` claim and a `/auth/me` without `session` count as probation.
- **Step-ups (F7):** only a passkey assertion (LP) or a `device_stepup` signature; never password, TOTP, recovery code or OIDC. Desktop and web step up only by passkey; on a PC without a passkey the UI says to use the Kaiku app on the phone (Q5). One grant per action; the action table is the C26–C29 common-rules table, copied once into `StepUpAction` on each platform.
- **No approval push in v1.0:** no `t=approval`, no approval list, no approval deep link; every approval starts with a scan or a typed code (B.2 Delivery). Notices never carry an approving action. Clients ignore `t=approval`, `approval_pending`, `approval_resolved` (reserved for v1.1).
- **Android key (CC1, B.1):** one Keystore P-256 key `K_approve`, non-exportable, hardware-backed (TEE, StrongBox where available), UV on every signature; API 30+ `setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG | AUTH_DEVICE_CREDENTIAL)` with a BiometricPrompt and CryptoObject per signature; API 26–29 a Class 3 biometric per use, or with only PIN/pattern/password a 10 s window opened by a credential prompt shown immediately before each signature; `setInvalidatedByBiometricEnrollment(false)`; never replaced silently; no possession-only key class.
- **Screen hardening:** `FLAG_SECURE` and `filterTouchesWhenObscured` on approval, setup, code and recovery-code screens; lock-screen notifications `VISIBILITY_PRIVATE`; no notification action approves anything.
- **Origin pinning (B.1, C27):** a configured app (it has a session or a key) accepts only payloads whose origin (scheme, host, port) equals its server's origin; it ignores any server a payload names. Only an unconfigured app accepts a new origin, from a setup payload, and shows `server_name` from the open first. **Coordinator call (2026-11-03), call 6:** a session or a key ties the app to its server; a saved server URL alone does not.
- **Accessibility (spec Constraints, older users):** codes shown in groups ("123 456"); a large digit keypad that allows corrections and never auto-submits; no gesture-only action; Android approval, setup and keypad buttons ≥ 64 dp, other actions ≥ 56 dp, code digits ≥ 32 sp, body ≥ 18 sp on these screens, respecting font scale; web primary buttons ≥ 48 px high and every control reachable by keyboard with a visible label.
- **UI contrast (CLAUDE.md):** readable text `text-text-primary` / `text-text-secondary` (Compose `onBackground`/`onSurface`, `onSurfaceVariant`); accent colours only for decorative indicators; never accent text on accent backgrounds; no opacity below 50 % on readable text; `text-text-muted` instead of `text-white/40`; severity shown by icon + text, not colour alone.
- **i18n:** web keys in `client/src/i18n/en/<area>.ts`, segments must match `^[a-z][a-zA-Z0-9]*$` (`client/scripts/check-i18n.ts` `KEY_RE`), so C28's `security.notice.<event_type>` is written with the camelCase event type (`security.notice.signIn`), which `toAndroidName` maps to C28's Android name `security_notice_sign_in`; keys are used through literal maps (no template-literal keys); `bun run i18n:sync` fills `locales/de.json` with empty values. Android strings in `res/values/strings.xml` only; `values-de` stays empty (C17); ViewModels expose `@StringRes Int`; Android `UnusedResources` is a lint error, so every string is referenced through a literal `when`.
- **Licences:** new Android deps `androidx.biometric:biometric:1.1.0` (Apache-2.0) and `com.google.zxing:core:3.5.3` (Apache-2.0), recorded in `LICENSE_COMPLIANCE.md`; no new npm or Rust dependency.

## Review Focus

1. **The PC's QR code changes, expires or loses the network while someone is scanning.** The QR rotates every 60 s without a new attempt and without resetting anything; a phone that scanned the old one gets "This code has just changed – scan the new one"; after 10 minutes the PC offers a fresh code; a dropped poll retries and keeps the attempt. Pinned in Task A3 (`QR rotates when a poll returns a new payload`, `network error while polling retries and keeps the attempt`, `expired attempt offers a new code`) and Task B8 (`stale token shows the changed-code text`).
2. **A phone setup that waits 24 hours, across app restarts and reboots.** The new phone keeps showing when it will be ready, never falls back to a login form, activates by itself at `ready_at` (device-key sign-in), and shows "Setup cancelled" if someone cancels. Pinned in Task B6 (`pending state survives a new repository instance`) and Task B9 (`pending setup resumes at app start and signs in when active`, `cancelled pending setup shows the cancelled screen and forgets the key`).
3. **A mistyped 6-digit code.** The digits are shown grouped, can be corrected before sending, are never sent automatically, and a wrong code says how many tries are left; the third ends the setup with clear next steps. Pinned in Task A7 (`code entry never submits by itself`, `wrong code shows tries left`), Task B10 (`keypad deletes and corrects before confirm`, `third wrong code ends the enrolment`).
4. **The phone's screen lock changes, a fingerprint is added, or UV fails.** A new fingerprint keeps the key; a removed screen lock (key invalidated) reports the device and shows how to set it up again, never replacing the key silently; a cancelled or locked-out prompt changes nothing on the server. Pinned in Task B3 (`biometric enrolment does not invalidate the key spec`, `invalidated key maps to KeyInvalidated`) and Task B6 (`invalidated key reports and forgets the device`).
5. **The wrong account or the wrong server on a shared device.** A configured phone refuses a QR or link of another server without any network call; a password-attempt QR of another account is refused; a setup code for someone else while signed in asks to sign out first; a second browser tab never triggers refresh-reuse. Pinned in Task B7 (`other origin is refused before any request`), Task B8 (`other account attempt shows the other-account text`), Task B9 (`setup for another user while signed in asks to sign out`) and Task A4 (`refresh runs under a Web Lock when available`).
