# v1.0 Family Release — Push Notifications (Phase 2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A family member's Android phone rings for every DM (text or photo) and every @mention, even when the app is closed or the phone is in doze. FCM is the default transport, UnifiedPush is the option, and the push payload stays content-free.

**Architecture:** Eight PR-sized tasks, server first (1–4), then Android (5–8). On the server, `server/src/push` gains an FCM HTTP v1 sender next to UnifiedPush and a `PushService` in `AppState`. A per-(user, channel) coalescer turns bursts into one leading push plus one trailing push. Push targets come from the Phase-1 shared dispatch helper `chat::send::dispatch_new_message`, so text and file messages are covered by the same code. The helper adds real per-user mention resolution. On Android there is one APK with both transports compiled in. Transport selection at runtime is a pure function. Receivers only parse the wake signal and enqueue an expedited WorkManager job. That job refreshes the token through Phase-1 `TokenRefresher.ensureFresh()`, fetches the new messages over REST, posts a grouped MessagingStyle notification that deep-links to the channel, and calls `ChatRepository.catchUp()` for a warm UI.

**Tech Stack:** Rust (axum 0.8, tokio, sqlx, reqwest 0.12, jsonwebtoken 10 `rust_crypto` — already in the tree, so **no new server crate**). Kotlin 2.1/Compose, Hilt 2.54, Ktor 3.1. New Android deps: WorkManager 2.10, hilt-work 1.2, Firebase Messaging (BoM), kotlinx-coroutines-play-services 1.9, UnifiedPush connector 3.x.

**Spec:** `docs/superpowers/specs/2026-10-20-v1-family-release-goal-design.md` (scope item 1; cut order)
**Review:** `docs/reviews/2026-10-22-v1-family-release-readiness.md` (B-05 push half, B-08, A-15; push design section of lane 4)
**Contracts:** `docs/superpowers/plans/2026-10-22-v1-family-contracts.md` (C1, C2, C5, C9, C10 used verbatim). New proposals C18–C21 are below.
**Builds on (open PRs, read-only):** server Phase-1 Task 7 `chat/send.rs` and Task 9 `pinned_client` + push https validation (#666); Android Phase-1 Tasks 2/4/6/8/9 (#660, #662) and Task 5 `ChatRepository.catchUp` (not yet opened).

## Proposed contracts (C18–C21; coordinator may renumber; do not edit the contracts file from a task)

**C18 — Push configuration discovery (server → Android)**
`GET /api/me/push-subscriptions/config` (authenticated) → `200 {"providers": ["unifiedpush"] | ["fcm","unifiedpush"], "fcm": {"project_id": "<firebase project id>"} | null}`.
`"fcm"` is listed only when the server has an FCM service account. Android uses FCM only when `fcm.project_id` equals the Firebase project baked into the APK.

**C19 — Per-device push registration (Android → server)**
`POST /api/me/push-subscriptions` body: `{"provider": "fcm"|"unifiedpush", "endpoint": string, "device_id": uuid, "device_label": string|null}`.
- `fcm`: `endpoint` is the FCM registration token (`^[A-Za-z0-9_:\-]{20,4096}$`). It is accepted only when FCM is configured; otherwise 400 `PUSH_PROVIDER_UNAVAILABLE`.
- `unifiedpush`: `endpoint` is an https distributor URL (Phase-1 Task 9 rules).
- Upsert key is `(user_id, device_id)`. A device holds exactly one subscription, so switching transport or rotating the token replaces it.
- Registering a `device_id` or an `(provider, endpoint)` removes rows that carry the same value under *other* users (shared or handed-down phone).
- Maximum 10 subscriptions per user; the least recently used rows are pruned.
- Response `201` is the existing `PushSubscription` view plus `device_id`. `device_id` stays optional for older clients, which keep the old `(user_id, endpoint)` upsert.
- `DELETE /api/me/push-subscriptions/device/{device_id}` → `204`, idempotent (also 204 when nothing matched).

**C20 — Wake signal wire format (server → Android)**
Kinds `t`: `"dm"`, `"mention"`, `"read"` (new: the channel was read on another device, so clear its notification), and `"call"` (reserved, not sent in v1.0). Receivers ignore unknown kinds (C5 spirit).
- **FCM**: a data-only message, never a `notification` block. `data` is `{"t": "...", "channel_id": "<uuid>", "count": "<decimal string>"}`; FCM data values are strings.
  `android.priority` is `"HIGH"` for `dm`/`mention` and `"NORMAL"` for `read`. `android.collapse_key` = channel id, `android.ttl` = `"86400s"`.
- **UnifiedPush**: unencrypted JSON body `{"t","channel_id","count"}`, with `count` as a number (unchanged from today).
- `count` is the number of messages this push stands for after coalescing. It is a hint for the fetch size, not an unread count.
- Coalescing per (recipient, channel): the first message pushes immediately; further messages within 10 s fold into one trailing push. At most 30 pushes per user per minute.
  A `read` signal goes out only if a dm/mention wake was sent for that (user, channel) in the last 24 h and has not been cleared yet.

**C21 — Mention syntax (server ↔ desktop/web/Android composers)**
- A mention is `@username`:
  - It starts the text or follows whitespace or one of `( [ { < " ' ,`.
  - The username is `[A-Za-z0-9_]{3,32}`, compared lowercased.
  - It is not inside a fenced or inline code span.
  - `@everyone` and `@here` follow the same boundary rule.
- Composers must insert `@username`, never the display name.
- Push targets are resolved per recipient: only real users with access to the channel, not the author, and no block in either direction.
  - `@everyone` pushes every member with channel access, capped at 100.
  - `@here` never pushes (its audience is online by definition).
- `MessageResponse.mention_type` keeps its message-level meaning but is now computed with this tokenizer. E-mail addresses and code no longer count.
  *Desktop follow-up (not in this plan):* the desktop sound/notification path treats `mention_type == "direct"` as "mentions me". It should also check its own username in the content.

## Review Focus

1. **FCM rejects a request because of a bug in our payload (HTTP 400 `INVALID_ARGUMENT`)**: every family phone's token would be pruned and push would silently die for everyone. Expected: only `UNREGISTERED` (404) and `SENDER_ID_MISMATCH` (403) prune; a 400 is logged and kept. Tests: `classify_400_invalid_argument_is_failed_not_gone` and `test_fcm_400_keeps_subscription` (Task 1).
2. **The push wakes a dead app whose 15-minute access token has long expired, possibly with no network yet** (the normal case after doze). Expected: refresh first; a network error means WorkManager retries; never a silent drop and never a logout. Tests: `network error on refresh returns RETRY` and `expired token is refreshed before fetching` (Task 6).
3. **A phone handed to another family member, or a logout followed by another account's login**: the previous account's pushes must stop reaching that device. Tests: `test_device_id_moves_to_new_user` (Task 2) and `logout deletes device subscription before tokens are cleared` (Task 7).
4. **A burst (20 photos in a DM, a lively group chat)**: there should be no 20 buzzes. Expected per (recipient, channel): one immediate push plus at most one trailing push per 10 s, and the phone shows one updated notification per channel. Tests: `burst_of_20_yields_one_leading_and_one_trailing` (Task 4) and `second wake fetches only messages after last notified id` (Task 6).
5. **"Mentions" that are not mentions, or that name people outside the channel** (e-mail address, code snippet, a user without access to a private channel): there should be no push, because a push to someone without access leaks that the channel is active. Tests: `test_email_and_code_are_not_mentions` and `test_mention_targets_only_members_with_access` (Task 3).
