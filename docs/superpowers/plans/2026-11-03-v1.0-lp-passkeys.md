# v1.0 LP: passkeys (server and all clients) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

## Re-alignment 2026-11-03 (spec rev 5, C29)

The first version of this plan (49bf88a9) was written against spec revision 2 and its own "C29 proposal". Spec revision 5 (frozen, d6ca7109) and the frozen C29 with the C26–C29 common rules (contracts e63da91a) now bind; where this plan and they disagree, they win. What changed:

1. **Desktop flow (F1 rev 4, C29 steps 1–7).** Listener first: the app binds `127.0.0.1:0` (the literal address) before anything else and draws a per-flow `callback_path` (32 bytes, b64u) and a verifier. One start (`POST /auth/passkeys/desktop/flows`, `loopback_port` + `callback_path` + `client_challenge`) and one redemption (`POST /auth/passkeys/desktop/redeem {flow_id, code, verifier}`) replace `desktop/login|step-up|register`, `exchange` and `exchange-session`. `finish` and `cancel` answer 200 with a **hand-off page** whose hashed script form-POSTs `flow_id` + `code` (or `error`) to `http://127.0.0.1:P/callback/<callback_path>`. The listener answers its own flow's POST with 200 "You can close this page", and anything else with 204, empty and without echo. The code is never rendered, logged or put in an address bar, redirect or API body; nothing takes effect before redemption, which re-checks the account, the passkey and (step-up) the session. The 303 `Location` with `code=`, `loopback_see_other` and the `redirect_uri` contract are gone. A missing desktop header gives `CLIENT_OUTDATED`.
2. **No passkey registration in the desktop app** (B.1 rev 3). The desktop register route, the Tauri `passkey_register` command and the desktop "Add" button are removed; desktop flows are `sign_in` and `step_up` only.
3. **Spike B added** (Task 1 input). Firefox, Chromium and Safari are checked for an insecure-form warning on the loopback form POST, and Chromium for Local Network Access, from a public `https` origin. The `fetch()` fallback with CORS and `Access-Control-Allow-Private-Network` ships only if the spike says so. The crate research (spike A), the `webauthn-rs =0.6.2` decision, the `=0.5.5` fallback and the 14-day rule are unchanged.
4. **"Browser for passkey sign-in"** desktop setting, the Linux/Firefox hint on the ceremony page and in the app, and the admin-guide note (F1, B.6.8).
5. **No interim first passkey.** Rev-2 DC1 (password + TOTP from a live session binds an account's first passkey at once) is removed, together with the `reauth` body, `InterimReauth`, `RegistrationVia::PasswordTotp` and `PASSKEY_REAUTH_UNAVAILABLE`. It would have let a known password + TOTP skip the bootstrap wait (F8, SM3).
   - Registration needs a full session and the grant `passkey.add`. Two step-ups produce that grant: an existing passkey (LP) and a key device's `device_stepup` (L1a).
   - So an account's first passkey comes from a full session that an L1a key device created (see item 12). L1b adds the account-request (incl. bootstrap), registration-ticket and setup-link paths.
   - No release candidate is cut before L1b (spec Sequencing).
6. **Sessions never change class** (CC4, rev 3). The rev-2 hook points are removed: a passkey step-up "upgrading" a probation session, and owner evidence (`last_owner_evidence_at`) in `record_use`. The probation banner's "Sign in with a passkey" is an ordinary F1 sign-in that creates a new session.
7. **Guards decide from committed rows** (B.4 rev 5). They are L1a's: the full-session guard and the step-up grant guard over `step_up_grants`. Both read committed rows, never a token alone or a positive cache. LP's grants record the passkey that produced it, and at use they are re-checked against the live session, that passkey and the action and target (F7 "At use"). Register finish and remove take L1a's account lock (B.7 rule 1).
8. **Step-up** needs a full session and returns `StepUpGrant {action, target, via: "passkey", expires_at}`, with `target` as C29's canonical string (`""` = none). An assertion by another account's passkey gives `PASSKEY_USER_MISMATCH`. `POST /api/admin/elevate {reason|null}` is L1a's and consumes `admin.elevate` from any producer, so LP changes no elevate code. `step_up: true` and `REAUTH_PASSKEY_REQUIRED` are dropped.
9. **Wire renames:**
   - passkey state `pending` (not `pending_activation`), with a stored `ready_at` (DC11);
   - the DTO is `Passkey` (with `ready_at`);
   - `PASSKEY_PENDING` 409 `{ready_at}` is new and never signalled as unknown;
   - `LAST_STRONG_AUTHENTICATOR` replaces `PASSKEY_LAST_STRONG_AUTHENTICATOR`;
   - `GET`/`PATCH /auth/passkeys` are open to any session;
   - ceremony and flow ids are random UUIDs (common rules).
10. **Device checks D1–D6** run after the LP merge, starting from a full key-device session (item 12, Q2); there is no dev-only seeding path. LP's own gate runs spike B and a virtual-authenticator check by hand.
11. **Unchanged:** the auth-package marks, the LP-1/LP-2 split after Task 10, the RP/origin/`assetlinks.json` work and the Android Credential Manager path. **Size:** ~7.0k insertions (server ~4.4k, clients ~2.6k), plus ~0.3k if spike B forces `fetch()`.
12. **Merge order L1a → LP → L1b** (coordinator decision, 2026-11-03; it replaces "LP merges first"). LP builds on L1a's merged session core instead of preparing interfaces for it:
    - L1a owns `issue_session()` (whoever lands first owns the extraction), the full-session guard, `step_up_grants`, the step-up action registry, `sessions.assurance` / `auth_methods` / `authenticator_id`, the B.7 account lock, the rule-2 cascade and `GET /auth/reauth/methods {passkey, device}`;
    - Task 1 now maps those names instead of extracting `issue_session`;
    - the interim Valkey grant store (old DC2) and the interim elevation path (old DC13) are dropped;
    - LP's migration adds `enrollment_id` itself, since the `passkeys` table does not exist when L1a's migration runs;
    - LP adds passkeys to L1a's strong-authenticator count, activation hook, label lookups and revocation cascade.

    L1a's interfaces are named here by their C26/C27 contract names. The L1 plan (`docs/superpowers/plans/2026-11-03-v1.0-login-server.md`) is still being written; Task 1 replaces those names with its Rust symbols.

**Goal:** Passkeys (WebAuthn L3, discoverable, UV required) as a first-class sign-in and step-up method in v1.0. That covers sign-in (discoverable and username-first) and step-up for sensitive actions; adding a passkey from a full session (the first one from a key device's session); and list, rename and remove. It runs on the web, on the desktop (system browser on Windows, macOS and Linux, for sign-in and step-up only) and in the Android app (Credential Manager). Also in scope: the registration core (`begin`/`complete`) that L1b's request, ticket and enrolment variants call. LP builds on L1a's merged session core (merge order L1a → LP → L1b).

**Architecture:**
- A new `server/src/auth/passkeys/` module wraps `webauthn-rs` in Kaiku's profile: RP ID = host of `PUBLIC_URL`; an exact origin allow-list incl. `android:apk-key-hash:` origins; resident key and UV required; BE fixed per credential.
- Ceremony state lives single-use in Valkey; credentials live in a new `passkeys` table with `state`, `ready_at` and `enrollment_id`.
- Sensitive actions consume L1a's action-bound, single-use step-up grants (`step_up_grants`); LP adds the passkey assertion as a producer (`via: "passkey"`) next to L1a's `device_stepup`. Sign-ins go through L1a's `issue_session()`, which makes a passkey session `full`.
- The desktop runs the ceremony on a server-rendered page in the system browser. A hand-off page posts a one-time code to the app's loopback listener, and the app redeems the code with its verifier.
- Android calls the same JSON endpoints through Credential Manager; the server publishes `/.well-known/assetlinks.json` from config.

**Tech Stack:** Rust/axum, `webauthn-rs` 0.6.2 (MPL-2.0, RustCrypto backend), sqlx/PostgreSQL, Valkey (fred); Solid.js (`navigator.credentials`), Tauri 2 (Rust loopback listener); Kotlin/Compose with `androidx.credentials` 1.6.0.

### Findings that change the package cut

1. **`webauthn-rs` no longer needs openssl.** 0.6.x (first stable 0.6 release: 0.6.2, 2026-10-31) verifies through `crypto-glue`, a facade over RustCrypto. openssl is in the server tree anyway (`native-tls` through reqwest 0.12 → openidconnect, and lettre), so neither version changes the server image.
2. **Three `webauthn-rs` defaults differ from the spec profile.** Fixed in Task 3:
   - registration requests `residentKey: "discouraged"`, which we change to `required`;
   - the allow-list assertion path accepts a BE upgrade, so we compare BE ourselves;
   - a counter that goes backwards refuses the assertion and cannot be switched off (design call DC4).
3. **Step-up and registration run on L1a's guards** (F7, C29, merge order L1a → LP → L1b). A step-up is a single-use grant for one action and target, made only from a full session; password + TOTP is not one. L1a ships the full-session guard, `step_up_grants`, the action registry and `device_stepup`; LP adds the passkey producer and extends L1a's at-use check to passkeys. Registration needs a full session and the grant `passkey.add`. An account's first passkey therefore comes from a key device's full session (DC1).
4. **The Custom Tab fallback is cut** (B.1, CC5): on Android, only Credential Manager.
5. **`PUBLIC_URL` is not set in `infra/compose/docker-compose.yml` today.** Making it mandatory breaks every install that lacks it. Task 2 sets it in compose and `.env.example`, and the CHANGELOG lists it under Changed.
6. **C29 is frozen** (2026-11-03) and supersedes this plan's earlier "C29 proposal" (re-alignment above).
7. **The desktop delivery is a loopback form POST, pending a browser spike** (F1, C29 step 7). Chromium's Local Network Access and the browsers' insecure-form warnings decide between the form POST and the `fetch()` fallback (spike B, before Task 9).

## C29 routes LP builds (frozen; the contract is authoritative)

Errors use the existing `{"error": CODE, "message": …}` body; option and credential JSON is the WebAuthn L3 JSON form (b64u), `options` = `{"publicKey": …}`, `credential` = `PublicKeyCredential.toJSON()`. "Full" is L1a's full-session guard (committed `sessions.assurance`, 403 `FULL_SESSION_REQUIRED`); "+ grant" is L1a's step-up grant guard over `step_up_grants` (403 `STEP_UP_REQUIRED`).

| Route | Auth | Body → answer | Limit |
|---|---|---|---|
| `POST /auth/passkeys/login/start` | public | – → `{ceremony_id, options}` (`allowCredentials: []`) | `AuthPasskey` |
| `POST /auth/passkeys/login/finish` | public | `{ceremony_id, credential, username\|null}` → 200 `AuthResponse` (`assurance: "full"`, `auth_methods: ["passkey"]` via L1a's `issue_session`; browser: refresh cookie; native: body) | `AuthPasskey` |
| `POST /auth/passkeys/step-up/start` | full | `{action, target}` → `{ceremony_id, options}` (`allowCredentials` = the caller's active passkeys) | per user |
| `POST /auth/passkeys/step-up/finish` | full, same `sid` | `{ceremony_id, credential}` → 200 `StepUpGrant` (`via: "passkey"`) | per user |
| `POST /auth/passkeys/register/start` | full + grant `passkey.add` (checked, not consumed) | `{label\|null}` → `{ceremony_id, options}` | per user |
| `POST /auth/passkeys/register/finish` | full, same `sid` | `{ceremony_id, credential}` → 201 `Passkey` (`active`; the grant is consumed here) | per user |
| `GET /auth/passkeys` | any session | → `{rp_id, user_handle, passkeys: [Passkey]}` (`pending` and `active`) | – |
| `PATCH /auth/passkeys/{id}` | any session | `{label}` → `Passkey` | per user |
| `DELETE /auth/passkeys/{id}` | full + `passkey.remove`/id | → 200 `{rp_id, user_handle, credential_id, remaining_credential_ids}` | per user |
| `GET /auth/reauth/methods` (L1a's) | any session | `{passkey, device}`: LP makes `passkey` true when the account has an active passkey | – |
| `POST /api/admin/elevate` (L1a's) | admin, full + `admin.elevate` | `{reason\|null}`; LP changes nothing, a passkey grant is consumed like a device one | as today |
| `POST /auth/passkeys/desktop/flows` | `X-Kaiku-Client: desktop`; public for `sign_in`, full bearer for `step_up` | `{purpose: "sign_in"\|"step_up", action\|null, target\|null, loopback_port, callback_path, client_challenge}` → 201 `{flow_id, url, expires_at}`; no header → 400 `CLIENT_OUTDATED` | `AuthPasskey` |
| `GET /auth/passkeys/desktop/{flow_id}` | public | ceremony page (HTML) | `AuthPasskey` |
| `GET /auth/passkeys/assets/ceremony.{js,css}` | public | static assets | – |

| `POST /auth/passkeys/desktop/redeem` | `X-Kaiku-Client: desktop`; for `step_up` the starting session's bearer | `{flow_id, code, verifier}` → `sign_in`: 200 `AuthResponse` with `refresh_token` + `purpose`, `user_id`; `step_up`: 200 `{purpose: "step_up", user_id, grant: StepUpGrant}`; any failure → 400 `PASSKEY_HANDOFF_INVALID` | `AuthPasskey` |
| `GET /.well-known/assetlinks.json` | public | C29 statements | – |

- `action`: any action of the step-up registry (common rules; L1a's enum and target checks). LP's own consumers are `passkey.add` (target `""`) and `passkey.remove` (target = passkey id); LP adds the target check for `passkey.remove` (the caller's active passkey). `target` is C29's canonical string (lowercase UUID, `others` or `""`).
- `StepUpGrant = {action, target, via: "passkey", expires_at}`. `Passkey = {id, label, state: "pending"|"active"|"revoked", created_at, last_used_at|null, ready_at|null, backup_eligible, backup_state, transports, aaguid}`.
- Codes LP returns: `PASSKEY_CEREMONY_INVALID` 400, `PASSKEY_INVALID` 400, `PASSKEY_UNKNOWN` 400, `PASSKEY_PENDING` 409 `{ready_at}`, `PASSKEY_USER_MISMATCH` 400, `PASSKEY_NOT_DISCOVERABLE` 400, `PASSKEY_ALREADY_REGISTERED` 409, `PASSKEY_LIMIT` 409, `LAST_STRONG_AUTHENTICATOR` 409, `PASSKEY_HANDOFF_INVALID` 400, `PASSKEYS_UNAVAILABLE` 503, `PASSKEY_CANCELLED` (hand-off `error` only), `CLIENT_OUTDATED` 400; through L1a's guards `FULL_SESSION_REQUIRED` / `STEP_UP_REQUIRED` 403.
- APK hash encodings and the `assetlinks.json` shape: the two C29 test vectors and statements, unchanged (Tasks 2, 10).

## Global Constraints

- **RP ID** = host of `PUBLIC_URL`: never a parent domain, immutable, checked at startup. `PUBLIC_URL` is mandatory; the server fails closed without it. Changing the domain invalidates every passkey and every key-device signature, and the admin guide says so. L1a already uses `PUBLIC_URL` as the signature origin; LP adds the RP-ID rules and the pin, and reuses L1a's parsing where it exists (Task 1).
- **Origin allow-list, exact strings, Android origins matched first:**
  - the web origin;
  - `android:apk-key-hash:<hash>` for every configured certificate, covering both APKs (`io.wolftown.kaiku`, `io.wolftown.kaiku.simple`) plus operator overrides for self-built APKs.

  In `clientDataJSON` the hash is the unpadded base64url SHA-256 of the signing certificate; `assetlinks.json` uses upper-case colon-separated hex. Padded or case-changed variants never match. Never list `tauri.localhost` or `tauri://localhost`; LP serves no `/.well-known/webauthn` (related origins).
- **Registration:** `residentKey: required`, `userVerification: required`, attestation `none`, `excludeCredentials`, `credProps`. Challenges are ≥16 random bytes, single use, and bound to the ceremony, the session (L1b: request, ticket or enrolment) and the account. It runs only in a browser or the Android app, never in the desktop app, and on the same client only from a full session with the grant `passkey.add` (from a passkey or a key device's `device_stepup`). An account's first passkey comes from a key device's full session (DC1).
- **Sign-in:** UV=1 is checked and UV=0 refused; BE must equal the value stored at registration; the signature counter is a signal, never an automatic lockout; `allowCredentials` is always empty. A `pending` passkey is answered `PASSKEY_PENDING` with `ready_at` and never signalled unknown.
- **Stored per credential:** AAGUID, BE/BS, transports, created, last used, state `pending` | `active` | `revoked`, and `ready_at` while pending.
- **After a delete:** `signalUnknownCredential` and `signalAllAcceptedCredentials` (where the client supports them).
- **Policy:**
  - a UV passkey assertion is a complete sign-in and gives a new full session (`assurance: "full"`);
  - a sign-in is not a step-up, and nothing upgrades a session;
  - removing the last strong authenticator (active passkeys and key devices together), or leaving an account password-only, is refused;
  - every add and remove is audited (L1b adds the notices).
- **Step-up** (F7): a single-use grant for one action and target, ≤5 min, bound to the session's `sid`, recording the authenticator that produced it, and made only from a full session (L1a's grants). A password, TOTP, a recovery code or OIDC, alone or together, is not a step-up. **At use**, L1a's grant guard consumes the grant inside the action's transaction only if:
  - the session's committed row is live and full;
  - that authenticator is still active (LP adds the passkey branch);
  - action and target match.
- **Sessions** (B.4 rev 5): LP adds no session check of its own. It uses L1a's guards, which decide from the committed `sessions` row read by primary key, never from a token alone or a positive cache; the Valkey denylist may only speed up a rejection. Revoking a passkey runs L1a's rule-2 cascade.
- **B.7 rule 1:** register finish and passkey removal run in one transaction that takes L1a's account lock first and re-checks under it.
- **Desktop** (F1, C29 steps 1–7):
  - The system browser, or the one chosen in "Browser for passkey sign-in", on all three OSes, for `sign_in` and `step_up` only.
  - The app binds `127.0.0.1:0` (the literal address) first, then starts the flow. The ceremony page names the purpose and the app and says "If someone sent you this link, close this page".
  - The one-time code (256-bit, b64u, stored as SHA-256, pending result 60 s) reaches the app only in the body of the hand-off page's POST to its loopback. It is never rendered, logged, or put in an address bar, a redirect or any API or polling response.
  - Nothing takes effect before redemption with code + verifier (+ the starting session's bearer for `step_up`), which re-checks the account, the passkey and the session.
  - Tokens stay in Rust. Flows live ≤10 min.
- **Android:** Credential Manager only (no Custom Tab fallback in v1.0). Passkey requests carry `X-Kaiku-Client: android`. `assetlinks.json` is generated from config with `get_login_creds` and `handle_all_urls`, `Content-Type: application/json`. The reverse proxy routes `/.well-known/` to the server, and Google must be able to fetch it.
- **Limits (B.5):** the per-IP block never applies to passkeys or signed-in sessions; passkey failures never feed `failed_auth`; the public passkey endpoints (challenges, desktop flows, redemption) have their own high, short-window request limit (`AuthPasskey`).
- Lifetimes: access 15 min, refresh 7 d sliding, L1a's absolute caps; LP changes none of them.
- **Licences** (CLAUDE.md, `cargo deny`): MIT, Apache-2.0, BSD-2/3, ISC, Zlib, CC0-1.0, Unlicense, MPL-2.0, Unicode-DFS-2016 only, for Rust, npm and Android alike. New, each recorded in `LICENSE_COMPLIANCE.md`:
  - the `webauthn-rs` family + `crypto-glue` (MPL-2.0, used unmodified);
  - `serde_cbor_2` (MIT OR Apache-2.0);
  - dev-only `webauthn-authenticator-rs` (MPL-2.0);
  - `androidx.credentials` 1.6.0 (Apache-2.0; `credentials-play-services-auth` pulls Play services client libraries under the Android SDK licence, as `firebase-messaging` already does).
- Wire fields `snake_case`; ids are UUID strings (common rules); web i18n in `client/src/i18n/en/*.ts` + `locales/de.json`; Android strings mirror web keys (C15); texts only through `errorText(code)` / string resources (C16). UI contrast rules (CLAUDE.md). Accessibility (spec): large targets, readable text, no gesture-only actions.
- Public repository: no private hostnames, IPs or secrets (use `chat.example.com`, `203.0.113.0/24`). Commits `type(scope): subject` with the `Co-Authored-By` trailer. Migrations get their timestamp at merge.

## Design calls (challenge these first)

- **DC1 (rev 5, merge order after L1a): the first passkey comes from a key device's full session.** On an Android app that is a key device, a `device_stepup` for `passkey.add` (C26) gives the grant, and `register/*` through Credential Manager adds the passkey. That passkey also works in browsers (synced through the phone's password manager, or over hybrid), and from such a full browser session further passkeys are added with a passkey step-up. A browser that has no full session gets its first passkey only through L1b's paths:
  - a `ready` account request, bootstrap included (F8, SM3);
  - a registration ticket (F8);
  - a setup-link enrolment (F5a, F5c; SM2).

  C29 allows an interim `reauth` body until L1a merges; with L1a merged first there is no interim, and a password + TOTP never binds a passkey.
- **DC2:** dropped (2026-11-03, merge order after L1a): L1a's `step_up_grants` is the only grant store.
- **DC3:** step-up uses `allowCredentials` = the caller's active passkeys, so a shared family PC shows only the right account; sign-in stays discoverable with an empty list. Kaiku checks BE equality on both paths.
- **DC4:** a counter regression refuses that assertion (crate behaviour, no switch) and writes the audit row `auth.passkey.counter_regression`. The credential stays active and other methods are unaffected, so it is not a lockout.
- **DC5:** the RP ID is pinned in `system_settings` (`passkeys.rp_id`). If the host changes while active passkeys exist, startup is refused unless `PASSKEY_ALLOW_RP_ID_CHANGE=<new host>`, which revokes them.
- **DC6:** at most 10 active passkeys per account (bounds `excludeCredentials` and step-up lists).
- **DC7 (rev 5): desktop delivery.**
  - The form POST is the default; `fetch()` is used only if spike B says so.
  - Per flow: one start, a ceremony page that may reload (fresh options each time), one finish, one redemption.
  - A failed finish or a cancel ends the flow (the app starts a new one). A successful finish keeps the flow only for its 60-s pending result.
  - Page texts are in English or German (`Accept-Language`).
- **DC8:** removal sets `state = 'revoked'` and keeps the row for audit; credential ids stay unique.
- **DC9:** `credProps.rk == false` refuses the registration (`PASSKEY_NOT_DISCOVERABLE`); a missing `credProps` is accepted.
- **DC10:** passkey sign-ins get tracing and metrics but no audit row (they are frequent; L1b's security events cover them).
- **DC11 (rev 5): `passkeys.ready_at` lives on the row.** Whoever creates a `pending` passkey (L1b) sets it, and it is set exactly while the row is pending. `PASSKEY_PENDING` and the `Passkey` DTO then need no join to `account_requests`.
- **DC12 (rev 5): `passkey.add` is refused on desktop flows** (400 `VALIDATION_ERROR`). The desktop app never registers (B.1), so such a grant could never be used.
- **DC13:** dropped (2026-11-03, merge order after L1a): L1a's `POST /api/admin/elevate {reason|null}` consumes `admin.elevate` from any producer, and C24 is gone.
- **DC14 (rev 5): "Browser for passkey sign-in"** offers `system` (default), `chromium`, `chrome`, `firefox` and, on macOS, `safari`, mapped to `tauri_plugin_shell::open::Program`. If the chosen browser cannot be started, the app says so and names the setting.
- **DC15 (rev 5): ceremony and flow ids are random UUIDv4 strings** (C29 common rules: ids are UUID strings; not UUIDv7, whose time prefix CC3 rules out for tokens). They are not secrets. The secrets are the WebAuthn challenge, the one-time code and the verifier, and knowing a flow id lets someone only cancel or restart that flow's ceremony.

## Review Focus

1. **`PUBLIC_URL` mistakes or a later domain change.** A trailing slash, upper case or a port must just work. `http://` on a real domain, a path, or an IP literal must stop startup with a message naming the fix. A domain change with existing passkeys must stop startup and explain the override, never silently break every passkey. Pinned in Task 2 (`rp_id_is_the_host`, `port_kept_in_origin_not_in_rp_id`, `http_only_for_localhost`, `ip_hosts_refused`) and Task 4 (`changed_rp_id_with_passkeys_refuses_start`, `allowed_change_revokes_and_moves_pin`).
2. **The family shares one public IP.** Failed or cancelled passkey attempts, by a relative or an attacker, never block that IP for password sign-in or anyone's passkeys, and passkey traffic has its own limit. Pinned in Task 5 (`failed_step_up_never_blocks_the_ip`), Task 7 (`failed_passkey_sign_ins_never_block_the_ip`, `passkey_requests_have_their_own_limit`) and Task 9 (`failed_redeems_never_block_the_ip`).
3. **Double submit, reload, back button, second tab.** A ceremony is single use: a repeated finish answers `PASSKEY_CEREMONY_INVALID` and never creates a second passkey, session or grant. A reloaded desktop page gets fresh options; two removals in parallel never leave an account without a passkey. Pinned in Task 6 (`ceremony_reuse_is_refused`, `concurrent_finishes_respect_the_limit`), Task 7 (`ceremony_is_single_use`), Task 8 (`concurrent_removals_keep_one_passkey`) and Task 9 (`reloaded_page_gets_fresh_options`, `finish_is_single_use`).
4. **The wrong account on a shared device.** None of these signs anyone into an account they did not choose or confirms an action for someone else: grandma's passkey picked while "fabian" is typed; a forwarded desktop link; another user's passkey in a step-up, web or desktop. Pinned in:
   - Task 7: `username_hint_mismatch_is_refused`;
   - Task 9: `forwarded_link_code_is_useless`, `step_up_by_another_accounts_passkey_is_user_mismatch`, `step_up_redeem_needs_the_starting_session`;
   - Task 5: `other_users_passkey_cannot_step_up`.
5. **The loopback listener and the code.** A page or program on the same computer that posts to the port gets 204, nothing echoed, and the listener keeps waiting. The code never appears in a URL, a redirect, a rendered page or an API body, and every redemption attempt spends it. Pinned in Task 9 (`code_is_never_in_a_url_or_api_body`, `wrong_verifier_spends_the_code`, `flow_id_and_verifier_without_code_never_redeem`) and Task 11 (`listener_answers_204_to_everything_else`, `listener_is_bound_before_the_start_request`).
6. **No shortcut to a first passkey or to full access.** A password + TOTP body never registers a passkey; a passkey sign-in is never a step-up; a grant dies with its session and with the passkey that produced it. A probation session never registers a passkey. Pinned in Task 6 (`reauth_body_is_not_a_step_up`, `account_without_strong_authenticator_cannot_register`, `probation_session_cannot_register`, `first_passkey_from_a_key_device_session`), Task 8 (`sign_in_is_not_a_step_up`) and Task 5 (`grant_dies_with_the_session`, `grant_dies_with_its_passkey`).
7. **Losing or removing passkeys.** Removing the last strong authenticator (passkey or, through L1a's route, key device) is refused with text that says what to do; removing a passkey ends the sessions it created. A removed passkey is signalled to the browser so it stops being offered. Signing in with a passkey the server no longer knows gives "This passkey was removed from Kaiku"; a `pending` one gives "ready at …" and is never signalled. Pinned in Task 8 (`last_passkey_cannot_be_removed`, `key_device_removal_counts_passkeys`, `removing_a_passkey_ends_its_sessions`, `removal_response_carries_signal_data`), Task 7 (`unknown_credential_is_reported`, `pending_passkey_gets_ready_at`) and Task 12 (`PASSKEY_UNKNOWN signals the credential and shows the removed message`, `PASSKEY_PENDING shows the ready time and signals nothing`).
