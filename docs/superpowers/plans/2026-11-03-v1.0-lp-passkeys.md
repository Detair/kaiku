# v1.0 LP: passkeys (server and all clients) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Passkeys (WebAuthn L3, discoverable, UV required) as a first-class sign-in and step-up method in v1.0: registration, sign-in (discoverable and username-first), step-up for sensitive actions, list/rename/remove, on web, on the desktop (system browser on Windows, macOS and Linux) and in the Android app (Credential Manager), plus the `issue_session()` extraction that L1a and L1b reuse.

**Architecture:** A new `server/src/auth/passkeys/` module wraps `webauthn-rs` in Kaiku's profile (RP ID = host of `PUBLIC_URL`, exact origin allow-list incl. `android:apk-key-hash:` origins, resident key and UV required, BE fixed per credential). Ceremony state lives single-use in Valkey; credentials live in a new `passkeys` table. Sensitive actions consume an action-bound, single-use step-up grant (`server/src/auth/step_up.rs`), which a passkey assertion creates. The desktop runs every ceremony on a server-rendered page in the system browser and gets back only a one-time code through the existing loopback hand-off pattern (S256 verifier, 60 s). Android calls the same JSON endpoints through Credential Manager; the server publishes `/.well-known/assetlinks.json` from config.

**Tech Stack:** Rust/axum, `webauthn-rs` 0.6.2 (MPL-2.0, RustCrypto backend), sqlx/PostgreSQL, Valkey (fred); Solid.js (`navigator.credentials`), Tauri 2 (Rust loopback listener); Kotlin/Compose with `androidx.credentials` 1.6.0.

**Spec:** `docs/superpowers/specs/2026-11-02-phone-key-login-and-simple-app-design.md`, **revision 2** (commit fbd02b4f): B.1 "Passkeys", F1, F7, B.4, SM3, SM6, Constraints, Sequencing (LP). Package cut (coordinator's working notes, 2026-11-03): LP in 2.2, hotspots 2.4, risks 4–6. Standards analysis: `login-best-practices.md` C1–C4 (working notes).

**Package class: auth.** Security critical (`server/src/auth`). Merge needs the maintainer's explicit OK. Three-reviewer rule: **Fable + Codex + Gemini Argon** review the PR; every task also gets the Faramir security pass in subagent-driven development; LP is part of the Fable final review of all v1.0 auth changes before the tag.

**Branch / PR:** `feature/lp-passkeys`, squash-merged, merges before L1a. Size estimate ~7.5k insertions incl. tests (server ~5k, clients ~2.5k), above the ~7k auth threshold. **PR boundary:** if the diff passes 7k, split after Task 10: **LP-1** (server, Tasks 1–10) and **LP-2** (clients, Tasks 11–14, stacked on LP-1). Both are auth PRs under the three-reviewer rule. Task 15 runs for each.

### Findings that change the package cut

1. **`webauthn-rs` no longer needs openssl.** 0.6.x (first stable 0.6 release: 0.6.2, 2026-10-31) verifies through `crypto-glue`, a facade over RustCrypto. openssl is in the server tree anyway (`native-tls` through reqwest 0.12 → openidconnect, and lettre), so neither version changes the server image.
2. **Three `webauthn-rs` defaults differ from the spec profile.** Fixed in Task 3: registration requests `residentKey: "discouraged"` (we change it to `required`); the allow-list assertion path accepts a BE upgrade (we compare BE ourselves); a counter that goes backwards refuses the assertion and cannot be switched off (design call DC4).
3. **Revision 2 changed step-up.** A step-up is a single-use grant for one action and target (F7), and password + TOTP is no longer one. LP adds `auth::step_up` with that interface, backed by Valkey. L1a moves the storage to `step_up_grants` and adds the device and `reauth` methods without touching call sites. The first passkey of an account needs an authority. LP uses the bootstrap factors of F8 (password + TOTP from a live session) without the bootstrap window, which L1b adds (DC1, Q2).
4. **The Custom Tab fallback is cut** (rev 2, B.1): on Android, only Credential Manager.
5. **`PUBLIC_URL` is not set in `infra/compose/docker-compose.yml` today.** Making it mandatory breaks every install that lacks it. Task 2 sets it in compose and `.env.example`, and the CHANGELOG lists it under Changed.
6. **Contract C29 does not exist yet.** The section "C29 proposal" below is LP's input to the freeze. If the frozen C29 differs, C29 wins, and this plan is updated before Task 5.

## C29 proposal (wire contract)

Errors use the existing `{"error": CODE, "message": …}` body. Option and credential JSON is the WebAuthn JSON form (base64url without padding), as `webauthn-rs` serialises it.

| Route | Auth | Body → answer |
|---|---|---|
| `POST /auth/passkeys/login/start` | public, `AuthPasskey` limit | – → `{ceremony_id, options: {publicKey}}`, `allowCredentials: []` |
| `POST /auth/passkeys/login/finish` | public, `AuthPasskey` | `{ceremony_id, credential, username?}` → `AuthResponse` (+ refresh cookie for browsers, as `/auth/login`) |
| `POST /auth/passkeys/step-up/start` | bearer | `{action, target?}` → `{ceremony_id, options}` (`allowCredentials` = the caller's active passkeys) |
| `POST /auth/passkeys/step-up/finish` | bearer, same `sid` | `{ceremony_id, credential}` → `{action, target, expires_at}` |
| `POST /auth/passkeys/register/start` | bearer | `{label?, reauth?: {password, mfa_code}}` → `{ceremony_id, options}` |
| `POST /auth/passkeys/register/finish` | bearer, same `sid` | `{ceremony_id, credential}` → 201 `PasskeySummary` |
| `GET /auth/passkeys` | bearer | → `{rp_id, user_handle, passkeys: [PasskeySummary]}` |
| `PATCH /auth/passkeys/{id}` | bearer | `{label}` → `PasskeySummary` |
| `DELETE /auth/passkeys/{id}` | bearer + grant `passkey.remove`/`{id}` | → `{rp_id, user_handle, credential_id, remaining_credential_ids}` |
| `GET /auth/reauth/methods` | bearer | gains `passkey: bool` |
| `POST /api/admin/elevate` | bearer, admin | also `{step_up: true, reason?}` (consumes grant `admin.elevate`) |
| `POST /auth/passkeys/desktop/login` | public, `X-Kaiku-Client: desktop` | `{redirect_uri, client_challenge}` → `{url}` |
| `POST /auth/passkeys/desktop/step-up` | bearer, `X-Kaiku-Client: desktop` | `{redirect_uri, client_challenge, action, target?}` → `{url}` |
| `POST /auth/passkeys/desktop/register` | bearer, `X-Kaiku-Client: desktop` | `{redirect_uri, client_challenge, label?, reauth?}` → `{url}` |
| `GET /auth/passkeys/desktop/{ceremony_id}` | public | ceremony page (HTML) |
| `POST /auth/passkeys/desktop/{ceremony_id}/options` | public | → `{ceremony: "get"\|"create", options}` |
| `POST /auth/passkeys/desktop/{ceremony_id}/finish` | public, form `credential` | 303 → `redirect_uri` + `code=` (or `error=CODE`) |
| `POST /auth/passkeys/desktop/{ceremony_id}/cancel` | public | 303 → `redirect_uri` + `error=PASSKEY_CANCELLED` |
| `POST /auth/passkeys/desktop/exchange` | public | `{code, verifier}` → `AuthResponse` with `refresh_token` (login codes only) |
| `POST /auth/passkeys/desktop/exchange-session` | bearer, same `sid` | `{code, verifier}` → step-up `{action, target, expires_at}` or 201 `PasskeySummary` |
| `GET /.well-known/assetlinks.json` | public | statements (below) |

- `action` ∈ `passkey.add` | `passkey.remove` (target = passkey id, required) | `admin.elevate`.
- `PasskeySummary = {id, label, created_at, last_used_at, backup_eligible, backup_state, transports, aaguid, state}`.
- Codes: `PASSKEY_CEREMONY_INVALID`, `PASSKEY_INVALID`, `PASSKEY_UNKNOWN`, `PASSKEY_USER_MISMATCH`, `PASSKEY_NOT_DISCOVERABLE`, `PASSKEY_ALREADY_REGISTERED` (409), `PASSKEY_LIMIT` (409), `PASSKEY_LAST_STRONG_AUTHENTICATOR` (409), `PASSKEY_REAUTH_UNAVAILABLE`, `PASSKEY_HANDOFF_INVALID`, `PASSKEYS_UNAVAILABLE` (503), `STEP_UP_REQUIRED` (403), `REAUTH_PASSKEY_REQUIRED`, and `PASSKEY_CANCELLED` (loopback only).
- **APK hash encodings (test vectors):** certificate SHA-256 bytes `00 01 … 1F` → `assetlinks.json` `"00:01:02:…:1E:1F"` and origin `android:apk-key-hash:AAECAwQFBgcICQoLDA0ODxAREhMUFRYXGBkaGxwdHh8`. SHA-256(`"kaiku-test-cert"`) → `"18:6F:F0:75:BF:FB:D4:76:5E:1C:5C:D9:E1:22:C4:09:44:58:A3:58:BC:E5:34:F5:3E:49:D7:B2:C3:81:AB:C0"` and `android:apk-key-hash:GG_wdb_71HZeHFzZ4SLECURYo1i85TT1PknXssOBq8A`. Android origins are matched before any generic URL handling, by exact string.
- **`assetlinks.json`:** one statement per app id: `{"relation": ["delegate_permission/common.get_login_creds", "delegate_permission/common.handle_all_urls"], "target": {"namespace": "android_app", "package_name": <id>, "sha256_cert_fingerprints": [<all configured certs, upper-case colon hex>]}}`. Header `Content-Type: application/json`. Empty Android config → `[]`.
- **Desktop hand-off:** the code leaves the server only in the 303 `Location` of `finish`. It is 32 random bytes in base64url, stored as SHA-256, valid 60 s, single use (any exchange attempt consumes it), and redeemed with the S256 verifier. The return address contract is the OIDC one (`oidc::is_loopback_client_redirect`). There is no polling route.

## Interfaces produced for L1a, L1b, L2 and E1

- `auth::step_up::{StepUpAction, StepUpVia, live_session, grant, consume}`: L1a swaps the Valkey store for `step_up_grants`, adds `StepUpVia::{Device, Reauth}` and the full-assurance check in `live_session`, and adds actions for its own routes.
- `auth::passkeys::register::{begin, complete, authorize_registration}`: L1b's enrolment variants (bootstrap, registration ticket, admin setup link, recovery) call `begin`/`complete` with `PasskeyState::PendingActivation` or `Active`. L1b replaces the `RegistrationVia::PasswordTotp` branch of `authorize_registration` with the SM2 `bootstrap` variant, including the window.
- `auth::passkeys::manage::ensure_not_last_strong(state, user_id, removing)`: L1a adds active key devices to the count.
- Hook points for L1a/L1b in LP code: `passkeys::reauth` step-up finish is where a passkey assertion upgrades a probation session (SM3); `queries::record_use` is where owner evidence is recorded (`last_owner_evidence_at`, SM7); L1b adds `StepUpAction`s for "That wasn't me" and Cancel by passkey assertion (B.2 rule table).
- `passkeys` table with `state` (L1a adds `activates_at` and `enrollment_id`); `PasskeyConfig { android_app_ids, android_cert_sha256 }` is the single source L1a's attestation check reads (E1 LP-A9).

- Client: `ReauthDialog` gains `onPasskey` and the method kind `passkey`; `lib/tauri/passkeys.ts::stepUpWithPasskey(action, target, signal)`. L2 rebases on both.

## Global Constraints

- **RP ID** = host of `PUBLIC_URL`: never a parent domain, immutable, checked at startup. `PUBLIC_URL` is mandatory; the server fails closed without it. Changing the domain invalidates every passkey, and the admin guide says so.
- **Origin allow-list, exact:** the web origin plus `android:apk-key-hash:<hash>` for both APKs (`io.wolftown.kaiku`, `io.wolftown.kaiku.simple`), plus operator overrides for self-built APKs. In `clientDataJSON` the hash is the unpadded base64url SHA-256 of the signing certificate; `assetlinks.json` uses upper-case colon-separated hex. Never list `tauri.localhost`; LP serves no `/.well-known/webauthn` (related origins).
- **Registration:** `residentKey: required`, `userVerification: required`, attestation `none`, `excludeCredentials`. Challenges are ≥16 random bytes, single use, and bound to the ceremony, the session and the account.
- **Sign-in:** UV=1 is checked and UV=0 refused; BE must equal the value stored at registration; the signature counter is a signal, never an automatic lockout; `allowCredentials` is always empty.
- **Stored per credential:** AAGUID, BE/BS, transports, created, last used, state `pending_activation` | `active` | `revoked`.
- **After a delete:** `signalUnknownCredential` and `signalAllAcceptedCredentials` (where the client supports them).
- **Policy:** a UV passkey assertion is a complete sign-in and gives a full session; a sign-in is not a step-up. Removing the last strong authenticator, or leaving an account password-only, is refused. Every add and remove is audited (L1b adds the notices).
- **Step-up** (F7): a single-use grant for one action and target, ≤5 min, bound to the session's `sid`. A password, TOTP, a recovery code or OIDC, alone or together, is not a step-up.
- **Desktop:** the system browser on all three OSes. The page says "Signing in to the Kaiku desktop app on this computer". Loopback redirect with a one-time code (the only way the code leaves the server); S256 verifier, 60 s, `no-store`, `no-referrer`; tokens only in Rust; step-up and registration bound to the desktop session's `sid`.
- **Android:** Credential Manager only (no Custom Tab fallback in v1.0). `assetlinks.json` is generated from config with `get_login_creds` and `handle_all_urls`, `Content-Type: application/json`. The reverse proxy routes `/.well-known/` to the server, and Google must be able to fetch it.
- **Limits (B.5):** the per-IP block never applies to passkeys or signed-in sessions; passkey failures never feed `failed_auth`; the public passkey endpoints have their own request limit (`AuthPasskey`).
- Lifetimes unchanged: access 15 min, refresh 7 d sliding (`server/src/auth/AGENTS.md`).
- Licences (CLAUDE.md, `cargo deny`): MIT, Apache-2.0, BSD-2/3, ISC, Zlib, CC0-1.0, Unlicense, MPL-2.0, Unicode-DFS-2016 only, for Rust, npm and Android alike. New: `webauthn-rs` family + `crypto-glue` (MPL-2.0, used unmodified), `serde_cbor_2` (MIT OR Apache-2.0), dev-only `webauthn-authenticator-rs` (MPL-2.0), `androidx.credentials` 1.6.0 (Apache-2.0; `credentials-play-services-auth` pulls Play services client libraries under the Android SDK licence, as `firebase-messaging` already does). Record each in `LICENSE_COMPLIANCE.md`.
- Wire fields `snake_case`; web i18n in `client/src/i18n/en/*.ts` + `locales/de.json`; Android strings mirror web keys (C15). UI contrast rules (CLAUDE.md). Accessibility (spec): large targets, readable text, no gesture-only actions.
- Public repository: no private hostnames, IPs or secrets (use `chat.example.com`, `203.0.113.0/24`). Commits `type(scope): subject` with the `Co-Authored-By` trailer. Migrations get their timestamp at merge.

## Design calls (challenge these first)

- **DC1 (interim first passkey):** an account without a strong authenticator registers its first passkey from a live session with password + TOTP (the F8 bootstrap factors) checked by `verify_reauth`. Password-only and OIDC-only accounts cannot do it in LP. This is not weaker than main today, where password + TOTP already gives a session that may change every factor. L1b restricts it to the bootstrap window (Q2).
- **DC2:** step-up grants in Valkey (`stepup:{sid}:{action}:{target|-}`, 300 s, GETDEL) behind the final interface; L1a moves them to `step_up_grants`.
- **DC3:** step-up uses `allowCredentials` = the caller's active passkeys (shared family PCs then show only the right account); sign-in stays discoverable with an empty list. BE equality is checked by Kaiku on both paths.
- **DC4:** a counter regression refuses that assertion (crate behaviour, no switch) and writes the audit row `auth.passkey.counter_regression`. The credential stays active and other methods are unaffected, so it is not a lockout.
- **DC5:** RP-ID pin in `system_settings` (`passkeys.rp_id`). If the host changes while active passkeys exist, startup is refused unless `PASSKEY_ALLOW_RP_ID_CHANGE=<new host>`, which revokes them.
- **DC6:** at most 10 active passkeys per account (bounds `excludeCredentials` and step-up lists).
- **DC7:** desktop `finish` is a form POST answered with 303 (a 307 would re-POST to the loopback). The page text is in English or German (`Accept-Language`). Login and session-bound codes use separate exchange routes.
- **DC8:** removal sets `state = 'revoked'` and keeps the row for audit; credential ids stay unique.
- **DC9:** `credProps.rk == false` refuses the registration (`PASSKEY_NOT_DISCOVERABLE`); a missing `credProps` is accepted.
- **DC10:** passkey sign-ins get tracing and metrics but no audit row (they are frequent; L1b's security events cover them).

## Review Focus

1. **`PUBLIC_URL` mistakes or a later domain change.** A trailing slash, upper case or a port must just work. `http://` on a real domain, a path, or an IP literal must stop startup with a message naming the fix. A domain change with existing passkeys must stop startup and explain the override, never silently break every passkey. Pinned in Task 2 (`rp_id_is_the_host`, `port_kept_in_origin_not_in_rp_id`, `http_only_for_localhost`, `ip_hosts_refused`) and Task 4 (`changed_rp_id_with_passkeys_refuses_start`, `allowed_change_revokes_and_moves_pin`).
2. **The family shares one public IP.** Failed or cancelled passkey attempts, by a relative or an attacker, never block that IP for password sign-in or anyone's passkeys, and passkey traffic has its own limit. Pinned in Task 5 (`failed_step_up_never_blocks_the_ip`) and Task 7 (`failed_passkey_sign_ins_never_block_the_ip`, `passkey_requests_have_their_own_limit`).
3. **Double submit, reload, back button, second tab.** A ceremony is single use: a repeated finish answers `PASSKEY_CEREMONY_INVALID` and never creates a second passkey or session; a reloaded desktop page gets fresh options. Pinned in Task 6 (`ceremony_reuse_is_refused`), Task 7 (`ceremony_is_single_use`) and Task 9 (`reloaded_page_gets_fresh_options`).
4. **The wrong account on a shared device.** Grandma's passkey picked while "fabian" is typed, a forwarded desktop link, or another user's passkey in a step-up never signs anyone into an account they did not choose and never confirms an action for someone else. Pinned in Task 7 (`username_hint_mismatch_is_refused`), Task 9 (`forwarded_link_code_is_useless`, `step_up_exchange_needs_the_starting_session`) and Task 5 (`other_users_passkey_cannot_step_up`).
5. **Losing or removing passkeys.** Removing the last passkey is refused with text that says what to do. A removed passkey is signalled to the browser so it stops being offered. Signing in with a passkey the server no longer knows gives "This passkey was removed from Kaiku", not a generic error. Pinned in Task 8 (`last_passkey_cannot_be_removed`, `removal_response_carries_signal_data`), Task 7 (`unknown_credential_is_reported`) and Task 12 (`PASSKEY_UNKNOWN signals the credential and shows the removed message`).
