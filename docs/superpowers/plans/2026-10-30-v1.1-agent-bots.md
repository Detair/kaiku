# v1.1 Agent Bots (Plan 3 of 3) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An AI agent (for example Hermes) lives in Kaiku chats as a bot. It is addressed by @mention, by a reply or in its own thread, and through slash commands, and it answers in place, including long-running answers. It sees only the channels its roles let it see. It reaches Kaiku either through an event adapter/bridge on the bot gateway (path A) or through bot tools on `/mcp` using its existing bot token (path B).

**Architecture:** Spec phases v1.1-d and v1.1-e.
- **Phase d, tasks 1–9.**
  - **Task 1** is a standalone security fix that can be cherry-picked into 1.0.x: bot message delivery honours the bot's effective `VIEW_CHANNEL`, the way a member's does.
  - **Bot permissions.** A bot's permission context comes from its guild installation: `@everyone`, the roles assigned to the bot user, and the channel overrides.
  - **Bot REST.** Bots get a `Credential::Bot` in `require_auth`, with a default-deny route allowlist and the per-bot rate limit. Over REST they use the **same message, reaction and typing routes as users**, so the checks are identical.
  - **Gateway actions.** WebSocket actions call the same handler cores.
  - **Interactions.** Slash commands gain deferred responses, edits and follow-ups within 15 minutes.
  - **Intents and identity.** A `mentions` intent, DMs to bots, an AI badge and a "bots that can read this channel" view complete the phase.
- **Phase e, tasks 10–15.**
  - **Path B:** `/mcp` accepts bot tokens as `McpPrincipal::Bot` and lists only `bot_*` tools. Each bot tool is a thin wrapper that child-dispatches to the bot REST routes, except `bot_wait_for_events`, which reads a bounded per-bot event buffer in Valkey.
  - **Path A:** a spike with a decision gate, followed by either a Hermes adapter or a generic bridge binary.

**Tech Stack:** Rust 1.95, axum 0.8, sqlx 0.9 (runtime queries), fred 10 (Valkey), utoipa 5.4, sha2 0.10, `subtle` 2.6 (added by plan 1), argon2 (legacy token verify only), tokio-tungstenite 0.29 + reqwest 0.12 (bridge). Client: Solid.js, vitest, UnoCSS, lucide-solid.

**Spec:** `docs/superpowers/specs/2026-10-30-mcp-admin-and-agent-bots-design.md` (sections 2 anti-goals, 3 last bullet, 5.1–5.4, 6 phases d+e, 7 "event buffer size"). Builds on plan 1 `docs/superpowers/plans/2026-10-30-v1.1-admin-mcp-core.md`, Interfaces I1 (`Credential`), I4 (`RouteTable`), I7 (`McpPrincipal`, `ToolCtx`, `OuterContext`, `dispatch`, `ToolResult`) and Task 11 (`/mcp` transport). Plan 2 is not required.

## Changes to plan 1 interfaces (apply in the named task; plan 1 itself stays unchanged)

1. **I1 `Credential`:** add the variant `Bot { bot_user_id: Uuid, application_id: Uuid }` (Task 2). `agent_token_id()` → `None`; `is_agent_token()` → `false`.
2. **I7 `McpPrincipal`:** add the variant `Bot { user: AuthUser, bot_user_id: Uuid, application_id: Uuid }` (Task 10).
3. **I7 `OuterContext`:** add `pub streaming: bool`, which is true when the `tools/call` response is SSE (Task 11). `bot_wait_for_events` needs it to keep non-streamed responses below the proxy timeout. Plan 1 sets it in `handle_post` after choosing the response mode.
4. **Task 11 `McpSession`:** add `#[serde(default)] pub kind: SessionKind`, where `enum SessionKind { #[default] Agent, Bot }`. For `Bot`, `token_id` holds the `bot_user_id`. The session-binding check compares `(kind, token_id)` (Task 10).
5. **Task 1 `AuditVia`:** add `Bot { application_id: Uuid }` (serialized `via: "bot"`) so the exhaustive match compiles (Task 2). The bot gate keeps bots off every audited route, so no entry should ever carry it.
6. **`CustomTool` / `map_child_response`** stay unchanged. Bot tools are a separate registry (`BotTool`, Task 10), because `CustomTool::calls()` must name `x-mcp` operations and `map_child_response` takes a `RoutePolicy`, and bot routes have neither.
7. **`TOOL_CALL_TIMEOUT` (45 s)** applies inside `dispatch()` only. `bot_wait_for_events` does not dispatch. Its wait is clamped to 40 s when `!streaming` and to 60 s when streaming (SSE keep-alive every 15 s). If plan 1's transport wraps all of `tools/call` in a timeout, Task 11 exempts this one tool.

## Global Constraints

- Spec 5.3 (verbatim): "Delivery must be filtered by the bot's effective `VIEW_CHANNEL` in that channel (role + overrides), exactly like a member. Private channels stay private unless the bot is explicitly allowed in."
- Spec 5.3: intent `mentions` = "deliver only messages that @mention the bot, reply to a bot message, or are in a thread the bot started. Default for agent bots; the existing `messages` intent (everything) stays for classic bots."
- Spec 5.3: `command_response` gains "a *deferred* mode … plus one or more follow-ups/edits within 15 min". DMs to bots are "gated by a per-bot setting (default off)". REST uses "`Authorization: Bot …`", with fast verification ("Argon2 per request would be a CPU DoS"). "Rate limits per bot as today."
- Spec 5.2 B (verbatim tool names): `bot_wait_for_events { timeout_s, types }` ("long-poll, max 60 s"), `bot_send_message`, `bot_reply`, `bot_respond_to_command`, `bot_update_response`, `bot_set_typing`, `bot_get_context { channel_id, around, limit }`. The endpoint is reached "with the bot's **existing bot token** … never with an agent token".
- Spec 5.4: "bot tools authorise **as the bot user**, never as its owner. No token can combine both." "Everything a bot receives from chat is untrusted input." Bots "never receive encrypted content".
- Maintainer decisions (spec §8) are untouched by this plan. Agent tokens remain system-admin-only and never reach bot routes.

## Review Focus

1. **Role allow vs `@everyone` deny on a private channel.** A bot holds role R with an override allowing `VIEW_CHANNEL`, and `@everyone` is denied. Expected: delivered. With only `@everyone` (no role): not delivered. With R's override denying while `@everyone` allows: not delivered. Tests: `role_override_lets_bot_into_private_channel` and `role_deny_hides_channel_from_bot` (Task 1).
2. **A bot uninstalled while still connected, or still holding roles after uninstall.** Expected: no further `message_created` or `message.created`, and its `guild_member_roles` rows are removed. Test: `uninstalled_bot_receives_nothing_and_loses_roles` (Task 1).
3. **Mention parsing edge cases.** `@HermesBot` in mixed case is a mention. `` `@hermesbot` `` in a code span, `@hermesbot_x`, `email@hermesbot` and `@everyone` are not. Test: `mention_rules_follow_c21` (Task 4).
4. **Two agent bots that mention or reply to each other.** Expected: bot-authored messages never count as addressed, so no `mentions`-intent loop. A bot never receives its own messages. Test: `bot_authored_messages_never_address_bots` (Task 4).
5. **Legacy Argon2 token upgrade racing a token reset.** Expected: the upgrade is a conditional `UPDATE … WHERE token_hash = <old>`, so a reset that happens in between wins and the old token stops working. Wrong secrets against a legacy hash are throttled (at most 10 Argon2 verifies per minute per bot). Tests: `upgrade_does_not_overwrite_reset_token` and `legacy_argon_attempts_are_throttled` (Task 2).

```rust
pub const SHA256_PREFIX: &str = "sha256:";
pub const LEGACY_VERIFY_LIMIT_PER_MIN: i64 = 10;
pub struct BotIdentity { pub bot_user_id: Uuid, pub application_id: Uuid }
pub fn generate(bot_user_id: Uuid) -> String;             // "<id>.<32 bytes OsRng base64url>"
pub fn hash_for_storage(token: &str) -> String;           // "sha256:" + hex(SHA-256(token))
pub async fn verify(state: &AppState, raw: &str) -> Result<BotIdentity, BotTokenError>;
pub enum BotTokenError { Invalid, Throttled, Internal } // Debug never prints the token
// auth/bot_gate.rs
pub const BOT_ROUTES: &[(&str, &str)] = &[
    ("GET",  "/api/messages/channel/{channel_id}"),
    ("POST", "/api/messages/channel/{channel_id}"),
    ("PATCH","/api/messages/{id}"),
    ("GET",  "/api/messages/{parent_id}/thread"),
    ("PUT",  "/api/channels/{channel_id}/messages/{message_id}/reactions"),
    ("DELETE","/api/channels/{channel_id}/messages/{message_id}/reactions/{emoji}"),
]; // Task 3 adds typing, Task 6 interactions, Task 10 /mcp
pub async fn gate_bot_request(state: &AppState, bot_user_id: Uuid, request: Request)
    -> Result<Request, AuthError>;
```
  `verify` steps:
  1. Split at the first `.` and parse the uuid, then look up `bot_applications` by `bot_user_id`.
  2. **Stored value `sha256:…`:** compare in constant time (`subtle`).
  3. **Stored value `$argon2…`:** check the throttle first: `INCR bot:auth:legacy:{id}` with `EX 60`; above `LEGACY_VERIFY_LIMIT_PER_MIN` → `Throttled`, without verifying. Then run the Argon2 verify on `spawn_blocking`. On success, `UPDATE bot_applications SET token_hash = $new WHERE id = $1 AND token_hash = $old` (a no-op if a reset happened in between).
  4. Anything else → `Invalid`.

  `authenticate()`:
  - `Authorization: Bot <t>` → `verify` → `find_user_by_id` → ban check → `AuthUser { session_id: None, credential: Credential::Bot { .. } }` → `gate_bot_request`.
  - `Throttled` → 401 `INVALID_TOKEN` (same as wrong secret).

  `gate_bot_request`:
  - The `MatchedPath` + method must be in `BOT_ROUTES`; otherwise 403 `BOT_TOKEN_NOT_ALLOWED`.
  - Rate limit: category `WsMessage`, identifier `bot_ws:{bot_user_id}` (the same budget as the gateway, 120/60 s). The outer `/mcp` request is not counted; its child requests are. Over the limit → 429 `RATE_LIMITED` with `retry_after`.
  - New `AuthError` variants: `BotTokenNotAllowed` → 403 `BOT_TOKEN_NOT_ALLOWED`; `BotRateLimited { retry_after }` → 429 `RATE_LIMITED`.

The 30 s timeout relay stays, and a deferral counts as a response for it.

## Decisions this plan settles (spec left them open or ambiguous)

1. **Bot permissions = installation + roles.** Bots are not `guild_members` today, and overrides exist only per role. The spec's "exactly like a member" therefore becomes: `@everyone` + the roles assigned to the bot user + channel overrides, through the same resolver. "Explicitly allowed in" means giving the bot a role that a private channel allows. This is why role assignment now accepts installed bots, and uninstalling a bot removes its roles.
2. **The visibility fix also covers outgoing app webhooks**, not only the gateway. Both leak the same content, and the fix fails closed on query errors.
3. **Bot REST reuses the user routes** (messages, reactions, history, typing) behind a `BOT_ROUTES` allowlist inside `require_auth`, instead of a parallel `/api/bot/*` API. Permission, content-filter and rate checks are then identical by construction, mirroring plan 1's parity idea. The gateway and MCP call the same cores. Consequence: the 1.0 `channel_members` check for bot sends is replaced by real channel permissions (CHANGELOG "Changed").
4. **Fast verification without new columns.** `token_hash` keeps its TEXT column with a scheme prefix (`sha256:` or Argon2 PHC). Legacy hashes are upgraded on the next successful verify, conditionally on the old value. The unsalted SHA-256 is safe because the secrets are random (122 bits for legacy UUID secrets, 256 bits for new ones). An in-memory cache was not chosen because it would delay revocation on token reset.
5. **`mentions` semantics.**
   - **Not addressing:** `@everyone`/`@here` never address bots; bot-authored messages never address bots (loop guard); a bot never receives its own messages.
   - **Precedence:** mention > reply > thread. "Threads the bot started" means threads whose parent message the bot wrote.
   - **Webhooks:** REST-only bots get a new webhook event `message.mentioned` instead of intent-filtered `message.created`, so existing webhook subscriptions keep their meaning.
6. **"Default for agent bots"** is applied when the owner marks the app as agent (`agent=true` adds `mentions` unless `messages` is set). An existing bot's stored intents are never silently changed.
7. **DMs to bots:**
   - only 1:1, and only when `dm_enabled` and the requester is the owner or shares a guild with the bot installed;
   - bots cannot start DMs;
   - every DM message counts as addressed (`mention_reason: "dm"`).
8. **Deferred responses.**
   - **Non-ephemeral:** a real placeholder message (`message_type 'deferred'`, a new allowed value) that the first update turns into the answer without an "edited" mark.
   - **Ephemeral:** a `command_deferred` event.
   - **Window:** the 15 minutes count from invocation, for both immediate and deferred responses.
   - **Limits:** at most 10 follow-ups per interaction. An unresolved deferral is cleaned up at the deadline.
   - Bot command responses now pass the content filter (they did not in 1.0).
9. **Slash commands are routed only to bots that can view the channel.** This is the same leak class as the must-fix, but it touches `messages.rs`, which changes often, so it lives in Task 3 and is **not** part of the 1.0.x cherry-pick.
10. **Bot MCP tools are a separate `BotTool` registry**; plan 1's `CustomTool` is untouched. The action tools child-dispatch to bot REST routes, so the gate, rate limit and permissions apply unchanged. Only `bot_wait_for_events` reads Valkey directly.
11. **Event buffer** (spec §7 left it to the builder):
    - 100 events per bot, TTL 10 minutes, cursor-based (`after`/`next_cursor`, so reads are not destructive and retries are safe);
    - buffering only while the bot has waited within the last 5 minutes;
    - one concurrent wait per bot;
    - the long-poll is ≤60 s with SSE, ≤40 s otherwise, to stay below a 60 s proxy timeout.
12. **"Bot badge (exists)"** is not accurate for v1.0: only webhook messages carry a badge. Task 7/8 add `is_bot` to the author profile and the Bot badge, as well as the AI badge.
13. **Rate limit.** The spec's "120/60 s" matches the `ws_message` default; `bot-system.md` still says 60 and is corrected. REST, gateway and MCP child calls share the one `bot_ws:{id}` budget.
14. **Bot users can never be system admins** (Task 10). Together with session-only agent-token creation, this makes "no token combines admin and bot" hold for every credential kind.
15. **Path A lives in this repo.** The Hermes adapter goes in `integrations/hermes-kaiku/` and the generic bridge is a second bin of `vc-server`, mirroring plan 1's `kaiku-mcp`. Exactly one of them is built, after a maintainer-approved gate.
