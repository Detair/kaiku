# v1.0 L1: server login (L1a core, L1b flows) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The v1.0 server side of the new login: device signatures and key devices, sessions with fixed assurance and an authoritative committed-session check, security notices in a read-only Kaiku DM (L1a); then every sign-in, setup, request and recovery flow on top of that core (L1b).

**Architecture:** A new `server/src/approvals/` core issues single-use challenges in the C26 signed format and verifies P-256 signatures from Android key devices; enrolment (SM2) creates key devices; device-key sign-in mints `full` sessions. Sessions record their assurance, client class and authenticator at creation; every request reads the committed `sessions` row by primary key (the Valkey denylist only rejects early), and every transition of B.7 runs in one transaction under account row locks taken in ascending id order. `server/src/security_events/` records append-only events with an audit row in the same transaction and delivers coalesced notices through an outbox into each user's read-only DM with the system account "Kaiku". L1b adds login attempts (SM1), account requests (SM3), the per-account throttles of B.5, registration tickets, the admin protocol, the upgrade migration and the host CLI's recovery commands.

**Tech Stack:** Rust/axum, sqlx/PostgreSQL (row locks, `LISTEN`/`NOTIFY`), Valkey (fred), `p256` (ECDSA verification only), `x509-parser` 0.16 (attestation properties), `hmac`/`sha2`/`hkdf`/`subtle`, `argon2`, `qrcodegen` (CLI). Server only; no client code.

**Spec:** `docs/superpowers/specs/2026-11-02-phone-key-login-and-simple-app-design.md`, **revision 5** (frozen, `d6ca7109`): B.0–B.7 (SM1–SM4 and the four rules), Part C, Constraints, Sequencing. Contracts: `docs/superpowers/plans/2026-10-22-v1-family-contracts.md` C26, C27, C28, and C29 where L1 touches passkeys (frozen, `e63da91a`). Package cut (coordinator working notes, 2026-11-03): L1a, L1b, LP in 2.2; hotspots 2.4; risks 4. Where the package cut disagrees with the spec or C26–C29, the spec and the contracts win.

**Package class: auth (every PR of this plan).** `server/src/auth` and `server/src/approvals` are security critical. Merging needs the maintainer's explicit OK. PR review: **Fable + Codex + Gemini Argon**; every task also gets the Faramir security pass during subagent-driven development; all of it is part of the Fable final review of the v1.0 auth changes before the tag.

**Merge order (coordinator decision 2026-11-03): L1a → LP → L1b.**

- **L1a depends on no LP code.** It starts on `main` and owns the `auth/session_issue.rs::issue_session()` extraction, the `PUBLIC_URL` origin, the step-up grant store with the full action registry (C27 common rules), the two guards and the strong-authenticator count. LP consumes them and adds the passkey step-up method, passkey sign-in and the passkey rows of the strong-authenticator count (interfaces below).
- **L1b is stacked on L1a** and may rely on LP's passkey routes being on `main`. Tasks 15–17 build on L1a's branch; rebase on `main` after LP has merged and before Task 18 (the first task that uses LP code: the hand-off page in Task 18, the passkey variants in Tasks 19, 22 and 23).
- The LP plan (`2026-11-03-v1.0-lp-passkeys.md`) is being re-aligned to rev 5 and C29; its names are provisional. **C29 is the source of truth** for every passkey route and field this plan touches.
- LP is not deployed to production before L1a + L1b + L2 (spec Sequencing). No RC is cut between these merges.

## Global Constraints

- Lifetimes: access JWT 15 min; refresh 7 d sliding; absolute from `created_at`: web 30 d, desktop 90 d, Android 90 d (B.4).
- Assurance is fixed at creation: `full` if and only if a passkey assertion (UV) or a device-key signature of an active key device created the session; every other session, including every session from before the upgrade, is `probation`; nothing changes it (CC4).
- Every authenticated request, every WebSocket and voice re-check (at least every 60 s), refresh and device-key sign-in decide from the committed `sessions` row read by primary key. A denylist hit rejects at once; a missing or unreachable denylist is skipped and never makes a session valid. **No positive cache** of live sessions; a later cache needs synchronous invalidation in the revoking commit path and a security review (B.4 rev 5).
- Revocation order inside the transaction: locks and re-checks → `ended_at` → denylist write (TTL ≥ access-JWT lifetime; a failed write does not stop the transition) → `NOTIFY` → commit; WebSocket and voice close through pub/sub after commit (B.4).
- Refresh rotates in place (stable `sid`); the immediate predecessor within 10 s gets the same successor, at most once per session per 24 h; any other earlier token ends the session (401 `SESSION_REUSED`, notice); an unrecognised token gets 401 and changes nothing.
- At most 50 live sessions per account (`MAX_SESSIONS_PER_USER`); a sign-in beyond that ends the least recently used session with a notice.
- Secrets (transfer tokens, codes, setup tokens, claim, collection and request secrets, tickets): 256-bit CSPRNG (codes: 6 digits), single use, stored only as an HMAC under a server key held outside the database, compared in constant time; never UUIDv7 (CC3, B.2 "Data model").
- Challenges: single use, consumed in the transaction of their effect, ≤10 min (DB CHECK). TTLs: `login` 2 min from the claim (attempt ≤10 min); `enroll` until the code expires (≤5 min); `device_login` 2 min; `device_stepup` 2 min (grant ≤5 min); `enroll_pop` the setup token's lifetime. All v1.0 kinds use the `login` limit class.
- Signed bytes, kind/variant/class bytes, `lp()` and canonical contexts exactly as C26; P-256 SPKI with an uncompressed point; verifiers accept high and low `s`; strings are hashed as the exact UTF-8 bytes sent in JSON (no normalisation, no trimming).
- Step-up: one action and target, ≤300 s, single use, bound to the `sid`, only for full sessions; methods: a passkey assertion (LP) or `device_stepup`. Never a step-up: password, TOTP, recovery code or OIDC, alone or together (F7).
- Enrolment: setup token 256-bit, 10 min, single use; code 6 digits, 5 min from the claim, 3 tries; ≤5 open per issuer; a request has at most one live child.
- Login attempt: QR token rotates every 60 s (a rotation resets no counter); collect ≤60 s after `approved`; attempt ≤10 min.
- Account requests: delay 24 h by default, 24–72 h (`ACCOUNT_REQUEST_DELAY_HOURS`); Finish within 24 h of `ready`; ≤3 `self` starts per account per delay period; one open request per account.
- B.5 defaults: an increasing per-account delay after 5 consecutive failures (from 30 s, doubling, ≤1 h); a notice at 20; `throttled` at 100; the recovery entry counts nothing per account before a valid recovery code; passkeys, QR login, device-key sign-in and existing sessions are never affected.
- Recovery codes: 10 single-use codes, 13 base32 characters each (65 bits), Argon2id. Passwords: optional, 8..128, offline blocklist of at least the top 100k breached passwords plus context words, no composition rules, Argon2id.
- Notices: coalesced per (recipient, subject, `event_type`) within 10 min; push `t=security` HIGH, collapse key `security-<notice_id>`, TTL `86400s`, at most one push per notice per 60 s; they bypass notification settings, `high` also quiet hours; no notice carries an approving action. No e-mail notices.
- No network signal in any decision: IP and place are display and audit data only; the client IP follows the trusted-proxy rule (`ratelimit::ip::extract_client_ip`); no external GeoIP call.
- `PUBLIC_URL` is mandatory; the signature origin is its ASCII origin (`https://chat.example.com`); the server fails closed at startup without it.
- v1.0 has no approval push, no open-approvals list and no number matching (B.2 "Delivery").
- Pre-session cookies and the refresh cookie: `__Secure-` prefix, `HttpOnly`, `Secure`, `SameSite=Strict`, paths per C26 common rules; the prefix is dropped only when `COOKIE_SECURE=false` (local development).
- Wire: C26–C29 common rules (snake_case, b64u without padding, RFC 3339 UTC, `{"error", "message"}` plus listed fields, UPPER_SNAKE codes listed in `server/src/error_code_tests.rs`, value lists append-only).
- Licences (CLAUDE.md, `cargo deny check`): MIT, Apache-2.0, BSD-2/3, ISC, Zlib, CC0-1.0, Unlicense, MPL-2.0, Unicode-DFS-2016 only, also for data files (password blocklist).
- Public repository: no private hostnames, IPs or secrets; use `chat.example.com` and `203.0.113.0/24`.
- Migrations: new files after every existing one (last on `main` today: `20261114000000_rollup_avg_sum.sql`); L1a uses `20261120…`, L1b `20261121…`; if `main` has later files at rebase (LP's passkeys migration sorts after L1a's), renumber the unmerged files keeping their order; never edit a merged migration. Use runtime `sqlx::query`/`query_as` as `auth/queries.rs` does; if a `query!` macro is added, refresh `.sqlx/` (Task 30).
- Commits: `type(scope): subject` (scopes `auth`, `db`, `api`, `ws`, `ratelimit`, `chat`, `crypto`, `infra`), ending with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. CHANGELOG entries under `[Unreleased]`, user perspective.

## Review Focus

1. **A slow approver.** A grandparent who stays on the context screen longer than the 2-min challenge, or takes longer than one challenge to type a code, must find the attempt open again with a fresh QR, or get a new challenge on the setup screen, never a dead flow. Pinned: Task 17 `slow_approval_after_challenge_expiry_returns_attempt_to_open`; Task 11 `expired_enroll_challenge_is_replaced_by_a_new_one`.
2. **Lost responses and retries.** A phone that loses the `/answer` response, a PC that loses `/collect`, a client that retries `/confirm` or `/finish`: a retry never mints a second session, grant or authenticator and never spends a try, and a status read tells the client what happened. Pinned: Task 10 `answer_retry_creates_no_second_grant`; Task 11 `confirm_retry_after_done_creates_no_second_device`; Task 17 `collect_retry_answers_ended_consumed`; Task 22 `finish_retry_does_not_reapply`.
3. **Valkey restarted or flushed mid-flow.** Attempts, enrolments, requests and sessions live in PostgreSQL, so flows continue; only counters and the denylist reset, and an ended session stays refused. Pinned: Task 6 `valkey_flush_keeps_ended_sessions_refused`; Task 11 `valkey_flush_mid_enrolment_completes`; Task 17 `valkey_flush_mid_attempt_still_collects`.
4. **Exact UTF-8 in signed display strings** ("Familie Müller", emoji in device names, composed versus decomposed umlauts, a trailing space): the server sends exactly the strings it hashed, so the phone's context-hash check never fails a genuine request. Pinned: Task 2 `strings_are_hashed_exactly_as_sent`; Task 17 `context_json_round_trips_exact_utf8`.
5. **Over-long or hostile self-reported labels** (a 300-character model name, control characters, bidi overrides in "a device calling itself …", an odd User-Agent): bounded and cleaned once at intake, then stored and signed exactly as stored. Pinned: Task 11 `label_is_cleaned_and_truncated_before_it_enters_the_context`; Task 17 `client_label_from_user_agent_is_bounded`.

## Design calls (challenge these first)

- **DC1 HMAC key:** `AUTH_HMAC_KEY` (64 hex chars) if set, else HKDF-SHA256 over the JWT signing key bytes with info `kaiku-auth-hmac-v1`. No new mandatory variable; rotating either key voids open attempts, enrolments, requests and tickets (they answer as unknown).
- **DC2 refresh reuse detection by authenticated format:** the EdDSA refresh JWT gains `sid` and `gen`; the row keeps the current generation, `refresh_jti` and `refresh_issued_at`, so the retry re-signs the identical successor (Ed25519 is deterministic). Legacy refresh tokens without `gen` are accepted once by hash and rotated into the new format.
- **DC3 legacy sessions:** probation, `auth_methods {legacy}`, `client_class web`, absolute cap `created_at + 30 d` (the strictest cap; the class is unknown).
- **DC4 ended rows:** kept 30 days (`end_reason`) for reuse recognition and audit, then deleted by the existing cleanup task.
- **DC5 close delivery:** `pg_notify('kaiku_session_ended', …)` inside the revoking transaction (PostgreSQL delivers it only on commit); a `PgListener` task republishes it as the existing `SessionNotice` on `user:{id}`. The ≤60 s socket re-check is the backstop. Works for the CLI process too.
- **DC6 one round trip:** the request check loads session row, user and ban state in one query, replacing `find_user_by_id` + `is_user_globally_banned` in `require_auth`.
- **DC7 test harness:** `helpers::generate_access_token` keeps its signature and uses the deterministic `sid` `Uuid::new_v5(TEST_SESSION_NS, user_id)`; `create_test_user` inserts that session as `full`. No production bypass, and the 455 existing call sites stay unchanged.
- **DC8 `p256`:** the version already in `Cargo.lock` (0.13.2), noted under the RUSTSEC-2026-0387 exception in `deny.toml` (verification on public inputs only). Re-check when LP brings the 0.14 stack.
- **DC9 attestation minimum:** `x509-parser` (in the tree) reads the leaf's key-attestation extension (OID `1.3.6.1.4.1.11129.2.1.17`); the chain is stored unverified (B.1).
- **DC10 Kaiku DM:** `channels.read_only` (true only for Kaiku DMs) instead of a participant lookup on every write.
- **DC11 notice outbox:** `security_events.delivered_at`; delivery is spawned after commit and re-driven by the minute sweep, so a crash or a CLI action delays a notice by at most a minute and never loses it.
- **DC12 single flight per key device:** a device-key sign-in ends the device's other live sessions (`superseded`), so "the device's current session" (B.1) is unique.
- **DC13 long-poll:** login-attempt and enrolment status long-polls re-read the row every 500 ms within `wait` (≤25 s); no attempt-bound pub/sub (single replica, C27).
- **DC14 blocklist:** SecLists `10-million-password-list-top-100000.txt` (MIT), stored gzip-compressed in `server/data/`, loaded once into a `HashSet` of lower-cased entries; context words: `kaiku`, the server name, username and display name (case-insensitive substring, ≥4 characters).
- **DC15 per-account counters** keyed by `SHA-256(lower(username))`, so unknown usernames count the same way without rows.
- **DC16 CLI:** a second binary `kaiku-admin` in `vc-server`, hand-parsed arguments (no new dependency), run with the server's environment inside its container (`docker compose exec server kaiku-admin …`); it writes rows and relies on the outbox and `NOTIFY` for delivery.
- **DC17 no local GeoIP database in v1.0:** `place` is `""` everywhere; `geoip.rs` and `GEOIP_API_URL` are removed.
