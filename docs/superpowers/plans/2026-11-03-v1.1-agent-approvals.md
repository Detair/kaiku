# v1.1 Agent Approvals (Package M2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An agent token can use `elevated` and `destructive` admin tools after its owner approves on one of their own devices. An approved elevation opens a 10-minute token window, and each destructive action is approved one by one. The owner approves with one confirmation: on the Android key device (UV), or on an enrolled desktop app for elevation windows. A TOTP page is the fallback.

**Architecture:** Spec phase v1.1-c, built on the v1.0 approvals core (package L1a). This plan adds no second mechanism.
- **Agent kinds.** M2 adds the agent kinds `agent_elevation` (0x10) and `agent_action` (0x11) and the desktop proof `agent_approver_pop` (0x12) to the v1.0 challenge core. They use the C26 signed bytes (`kaiku-sig-v1`) with their own canonical contexts. The stored agent request lives in the side table `approval_agent_requests`, and the owner's phone-only setting in `approval_owner_settings`.
- **Gate.** `OwnerApprovals` (M1's I5 hook in `approvals/agent_gate.rs`) turns every destructive agent request into `202 {approval_id}`. An elevation is requested on its own route.
- **Single execution path.** Execution re-dispatches the stored request through the fully layered router with an unforgeable `ApprovedExecution` extension.
- **Delivery.** M2 activates the items C26 reserves for v1.1: push `t=approval` to Android key devices, WS `approval_pending` / `approval_resolved`, and `GET /api/approvals?state=open`.
- **Approvers.** Desktop approver rows (platform `desktop`) answer agent kinds only, and never a v1.0 kind. A TOTP page serves as the fallback.

**Tech Stack:** Rust 1.95, axum 0.8, sqlx 0.9 (runtime queries), fred 10. The server verifies with `p256` 0.13, the dependency L1a added (public inputs only). Desktop: Tauri 2, `keyring-core` 1, `ring` 0.17 for signing (already in `Cargo.lock` through rustls; see Global Constraints). Android: Kotlin, Hilt, Ktor, WorkManager, Compose, and the v1.0 key-device signer. Client: Solid.js, vitest.

**Spec:** `docs/superpowers/specs/2026-10-30-mcp-admin-and-agent-bots-design.md`: §4.3 (revocation cleanup, default deny), §4.4 entirely, §6 (v1.1-c), §8, and the "Adjustments 2026-11-03" note. The v1.0 foundation it builds on is `docs/superpowers/specs/2026-11-02-phone-key-login-and-simple-app-design.md` (revision 5, frozen: B.2 mechanism and kinds, B.4 assurance, B.5 limit classes, B.7 state machines) and contract **C26** in `docs/superpowers/plans/2026-10-22-v1-family-contracts.md` (kinds 0x10–0x1F reserved for v1.1, the reserved `t=approval` push and WS approval events). Plan 1 (`2026-10-30-v1.1-admin-mcp-core.md`, package M1) supplies I1–I7, consumed verbatim. This plan replaces `2026-10-30-v1.1-owner-approvals.md`.

These names come from the package cut (§1.9, A1–A10) and from the frozen C26–C28 routes. Where the merged v1.0 code uses other names, use those names and keep the behaviour described here. If a hook is missing (for example a per-kind arm in the answer handler or the sweep), add it in the M2 task that needs it, with a test that every v1.0 kind still behaves as before.

- **A3** core queries `create_tx` / `approve_tx` / `deny_tx` / `consume_tx` / `expire_touched_tx` / `expire_due` over `approvals(id, kind, variant, approver_id, subject_id, device_id, requester_kind, requester_id, nonce, context_hash, display, state, created_at, expires_at, decided_at, consumed_at, limit_class)`, with states `issued → approved → consumed`, `issued → denied | reported` and `issued | approved → expired`.
- **A4** signing: `signing_prefix(row, device_id)`, the `lp`/`i64`/UUID encoders, `context_hash(kind, c)`, `verify(spki_der, msg, sig_der)`, `server_origin(config)` (fail closed), and the golden file `mobile/android/app/src/test/resources/golden/kaiku_sig_v1.json`.

- **A8** devices: `approval_devices(id, user_id, device_id, platform, public_key, label, state, enrolled_via, uv_class, …, revoke_reason)` with lookups for active devices by user and platform.

- **Security events** (C28): the writer used in the same transaction as the cause; the event-type list is append-only.
- **Label sanitising:** `sanitize_label(raw) -> String` (bidi and control characters stripped, whitespace collapsed, capped with "…").
- **TOTP** (L1b): the code check with its replay store (`auth::reauth::accept_totp` today), the TOTP state (`active` | `throttled` | `compromised`) and its generation.
- **Android (L2):** the key-device signer (UV per B.1), `ApprovalApi`, the `ApprovalChallenge` checker (B.2 "Before signing"), `ApprovalText`, the approval screen components, and `DeviceIdStore`.

## Global Constraints

- **Maintainer decisions (v1.1 spec §8, fixed):**
  - Agent-token elevation window **10 minutes**.
  - Approval = "**a notification on mobile or desktop that is simply confirmed**", signed by the owner's device; TOTP on the Kaiku approval page is the fallback; "**A password never counts.**"
  - **Destructive actions only from the phone**, on by default; desktop approvals cover elevation windows only.
  - **System admins first:** only agent kinds are admin-only. Key devices exist for every user since v1.0.
- **v1.0 rules (frozen, rev 5; binding here):**
  - Every signature is a C26 `kaiku-sig-v1` message; any change to signed bytes needs a new magic string.
  - Agent kinds use bytes from 0x10–0x1F. Challenges are single use and at most 10 minutes (DB CHECK).
  - **Desktop approval keys never answer a v1.0 kind** (`login`, `enroll`, `device_login`, `device_stepup`, `enroll_pop`). **A desktop row is never a key device or a strong authenticator.**
  - **Probation sessions approve and deny nothing** (B.4). Every owner answer for an agent kind needs a full session.
  - B.7 rules: one transaction per transition with its audit row; the sweep runs every minute; **consumption re-checks authorisation** (rule 4).
  - **Separate limit classes:** agent denials, agent counters and agent pushes never pause, slow or starve human sign-ins (CC9, K9). The agent push budget lives in Valkey: 6 per 10 minutes per device.
  - Every C26–C28 value list (kinds, step-up actions, event types, platforms, reasons) is append-only. Clients map unknown values to UNKNOWN (C5).
  - `APPROVAL_UNAVAILABLE` is C26's code with status **503**. The other C26 codes are reused where they fit (`APPROVAL_NOT_FOUND` 404, `APPROVAL_STATE` 409, `APPROVAL_EXPIRED` 410, `SIGNATURE_INVALID` 400, `KEY_DEVICE_REVOKED` 403, `TOO_MANY_ATTEMPTS` 429 + `Retry-After`, `SERVICE_UNAVAILABLE` 503).
- **v1.1 spec 4.4 values (verbatim):**
  - Approvals expire **5 minutes** from creation; "approving does not extend it".
  - "At most **3** open approvals per owner"; only unexpired `issued`/`approved` agent rows count.
  - Push: TTL = the challenge TTL (300 s), collapse key **`approval-<id>`**, "bypass the message coalescer and read gate", "only to the push subscriptions of enrolled approval devices".
  - "Approvals and the TOTP page **fail closed**" without `PUBLIC_URL`.
  - "A retry needs a new approval. Deny is final for that approval id."
- **Display (spec 4.4 step 2):** text comes from the **server-stored** request with **fixed wording per action**. Immutable ids appear next to names. Free-text labels are sanitised, capped and marked as labels. Agent free text appears only as a quoted "reason given by the agent". HTML is never interpreted on any client.
- **Agent tokens never** enrol, remove or list devices, read open approvals, review, answer, open the TOTP page or change approval settings. The default-deny gate refuses these routes (no `x-mcp`), and each handler also rejects `Credential::AgentToken` with 403 `AGENT_TOKEN_NOT_ALLOWED` (defence in depth).
- **Crypto and dependencies:**
  - The server only verifies, on public inputs, with L1a's `p256` 0.13 (under the RUSTSEC-2026-0387 exception).
  - **Desktop signing never uses `p256` 0.13**, because it would put a secret scalar on the crypto-bigint 0.5 stack that the advisory covers. Use `ring` 0.17 (`EcdsaKeyPair`, `ECDSA_P256_SHA256_ASN1_SIGNING`). It is already in `Cargo.lock` through rustls, and its licence entry exists in `deny.toml`.
  - If a `p256` release on elliptic-curve 0.14 with crypto-bigint ≥ 0.7.6 is usable when Task 11 is built, it is an acceptable alternative.
  - Task 11 updates the advisory comment in `deny.toml` either way.
  - No other new crates; `cargo deny check` stays green; no GPL/AGPL/LGPL.
- **Migration** `server/migrations/20261121000000_agent_approvals.sql` is a placeholder. Rename it so that it sorts after every v1.0 migration and after M1's two migrations, and before M3's `20261201000000`+.
- **Gates per task:**
  - Server: `cargo nextest run -p vc-server` (dev stack via `make docker-up`), `cargo fmt --check`, `SQLX_OFFLINE=true cargo clippy -p vc-server -- -D warnings`.
  - Client: `cd client && bun run test:run`.
  - Tauri: `cd client/src-tauri && cargo test`.
  - Android: `cd mobile/android && ./gradlew :app:testDebugUnitTest`.
- **Code conventions:**
  - Runtime `sqlx::query`/`query_as` only.
  - New error codes are UPPER_SNAKE and go into `server/src/error_code_tests.rs`.
  - i18n: `client/src/i18n/en/*.ts` + `client/src/i18n/locales/de.json`; Android `res/values/strings.xml` + `res/values-de/strings.xml`.
  - Wire fields are snake_case. CLAUDE.md contrast rules apply.
- **Secrets** (signatures, private keys, PKCS#8 bytes, CSRF tokens, TOTP codes, agent request bodies) never appear in logs, `Debug`, audit details or URLs. Write `Debug` by hand where a struct holds them.

## Review Focus

1. **A desktop approver counted as a key device by v1.0 code.** The paths at risk are:
   - strong-authenticator counts (`LAST_STRONG_AUTHENTICATOR`, owner action rule, independent cancellers);
   - device-key sign-in;
   - the `claim`, `step-up` and enrolment challenge routes;
   - a session's `authenticator_id`.

   Expected: never; a desktop row exists only for agent kinds. Test: `desktop_approver_is_never_a_key_device` (Task 3).
2. **A probation session answering an agent approval**, for example a PC signed in by QR that signs with a desktop key, denies, or uses the TOTP page. Expected: 403 `FULL_SESSION_REQUIRED`, and the challenge stays `issued`. Tests: `probation_session_cannot_answer_agent_approvals` (Task 5), `totp_page_requires_full_session` (Task 9).
3. **An agent starving human sign-ins.** A prompt-injected agent fills the open cap, the creation limits and the push budget, and then the owner signs in by QR. Expected: the `login` challenge, its limits and the login TOTP counters are untouched. Test: `agent_limits_never_touch_login_class` (Task 4).
4. **A valid signature used in the wrong place.** Cases:
   - an agent signature replayed on another approval, device or kind;
   - a desktop key answering a v1.0 kind;
   - a desktop key answering a destructive action while phone-only is on.

   Expected: `SIGNATURE_INVALID` or `APPROVAL_DEVICE_NOT_ALLOWED`, and the state is unchanged. Tests: `signature_bound_to_kind_approval_and_device` (Task 5), `desktop_cannot_answer_v1_0_kinds` (Task 5), `sign_refuses_v1_0_kinds` (Task 11).
5. **The approver is invalidated between approve and execute.** The approving device is removed, an admin uses "Remove device now", or TOTP is renewed. Expected (B.7 rule 4): execute refuses, the approval is `expired` with reason `approver_revoked`, and nothing runs. Test: `execute_rechecks_approver` (Task 7).

## Decisions this plan settles (spec left them open or ambiguous)

1. **Elevation has its own request route** (`POST /api/approvals/elevation` plus `elevation_request`). There is no implicit approval on each elevated call, which would spam the owner.
2. **No `GuildOwnerUnchanged` precondition.** Transfer of ownership is out of v1.1 scope (spec 3.1 rows 4–8).
3. **One approval per destructive action, never an extra window.** An approved execution counts as elevated for that single request only.
4. **The TOTP page answers every agent kind**, including destructive with phone-only on. The TOTP factor is not on the agent's PC, and the server cannot detect whether a device is reachable.
5. **Deny is unsigned** from any full owner session. It can only prevent an action; the audit records the device when known.
6. **Every owner answer needs a full session** (design call from v1.0 B.4: probation approves and denies nothing). On a PC that means a passkey sign-in; otherwise the phone approves (v1.0 B.6.8).
7. **Desktop approvers enrol from a full desktop session with a passkey step-up** (`agent_approver.add`) and an `agent_approver_pop` proof. There is no password or OIDC re-auth and no SM2 enrolment. A desktop row is never a key device, never answers a v1.0 kind, and is removed without a step-up.
8. **Desktop signing uses `ring`**, so no secret key touches the crypto-bigint 0.5 stack (RUSTSEC-2026-0387). The server keeps verifying with `p256` 0.13.
9. **Agent limits are their own class:** the open cap is counted from rows under the owner lock; the creation, TOTP-failure and push counters live in Valkey (v1.0 B.5) and fail closed (503) for creation.
10. **`APPROVAL_UNAVAILABLE` means "no `PUBLIC_URL`" (503, C26).** "No approver for this tier" is the new 403 `APPROVER_MISSING`, so clients can tell the two apart.
11. **Revocation-driven expiry sends no push or WS notice** (the cleanup hook has only a connection). Devices find out on their next fetch.
12. **The stored body is the canonical re-serialisation of the parsed JSON**, so the re-dispatched child hashes identically. Only JSON or empty bodies can be destructive.
13. **Consumption re-checks the approver** (v1.0 B.7 rule 4): a removed device, renewed TOTP or a re-enabled phone-only setting expires an approved-but-unexecuted request (`approver_revoked`).
